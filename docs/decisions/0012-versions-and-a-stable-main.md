# 0012: Versions for units, components and releases, and a stable `main`

**Date:** 2026-11-16. **Status:** accepted. Adds to [0007](0007-testing-releases-and-traceability.md).

## Context

[0007](0007-testing-releases-and-traceability.md) gave the whole repo one version and postponed versions for each unit. Since then:

- The repo builds a second firmware, for the Wi-Fi dongle ([0011](0011-wifi-dongle.md)), which changes at its own pace. A GUI and our camera firmware will follow.
- Units already carry versions in `library.properties`, and the build reports them (D4), but nothing checks that they change when their code does.
- `main` received increment 2's part 3 in one merge of three stacked pull requests (#35), which raised the question of how stable `main` should be between releases.

The maintainer wants components, such as the motor driver, to stay stable on their own, without tagging increments.

## Decision

### Four kinds of version

| Kind | Example | Its version says | Lives in |
|---|---|---|---|
| **Unit** | `board` (the motor driver), `safety`, `relay` | What its interface and behaviour are | its `library.properties` |
| **Component** | UNO firmware, dongle firmware, `conq`; later the GUI and camera firmware | What you flash or install | `firmware/<name>/VERSION`; `host/pyproject.toml` for `conq` |
| **Protocol** | 8 | Whether two components can talk | the firmware, reported in `{V}` |
| **Product** | open-conqueror 0.1.0 | A set of components tested together on the robot | the root `VERSION`, and the release tag |

All four use [Semantic Versioning](https://semver.org). Each component reports its own version: the firmwares in their version message, `conq` with `--version`.

### Units

- **A pull request that changes a unit's code gives it a new version.** MAJOR when other units must change to keep working with it, MINOR for new behaviour, PATCH for fixes. Before 1.0.0, MINOR covers breaking changes too.
- **CI checks it:** `dev.py units --base origin/main` fails if a unit's `src/` changed and its version didn't.
- **A stable unit** has a fixed interface, tests that pin its behaviour, and a version that changes only with its code. The changelog then shows, release by release, which units changed.

### Releases

- **One product release,** as in 0007: a tag such as `v0.1.0` on `main`, and a GitHub Release with every component's image, the test report and a manifest. The manifest lists each component's version, the protocol version and every unit's version, generated by `dev.py` when releases start.
- **Components aren't tagged or released on their own.** That comes back when a component gets users of its own, for example `conq` published on PyPI, or a GUI people install without a robot.

### A stable `main`, without tagging increments

Every merge into `main` leaves it flashable:

- CI passes on all three systems, and the firmware stays within the T8 limits.
- The change's own robot check has passed, recorded on its pull request.
- Behaviour that hasn't had its robot check yet is off by default, or waits.
- Pull requests target `main`. If one must build on another, merge the bottom one, delete its branch so GitHub retargets the next, and only then merge that (the lesson from #35).

Increments aren't tagged. The stable points are releases and their candidates.

## Consequences

- The root `VERSION` is now the product's version. The UNO firmware reads `firmware/uno/VERSION`, and the robot test `version_and_standby` checks the robot against it.
- `conq` keeps its own version and no longer has to match the firmware's. The protocol version is what they must agree on.
- CI fetches the full git history so it can compare units with the base branch.
- Generating the release manifest waits for the first release candidate.
