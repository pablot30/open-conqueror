# R1: Code quality and static analysis

**Recommendation in one line:** gate every merge with free, honest checks.

Research date: 8 November 2026. Sources are cited inline. Anything marked **[unverified]** was not confirmed against a primary source during this research, and "measured" means it was run on the maintainer's Mac.

The project should keep MISRA C++:2023 as its yardstick, but call itself **"MISRA C++:2023-informed"** rather than compliant. It should enforce that with a free stack: clang-tidy, open-source cppcheck and strict compiler warnings, plus the free MISRA Compliance:2020 process for recording exceptions. **No free tool checks MISRA C++:2023 fully.** Open-source cppcheck checks only MISRA C:2012. clang-tidy has no MISRA module. The best free partial checker, PVS-Studio, covers about 22 MISRA C++:2023 rules, and its open-source licence only fits once the repo is public. The 100% line, branch and MC/DC target in Q3 is achievable, but only for board-independent logic that is compiled and tested on a computer with Clang 19 or later. Apple Clang 21 already does this on the maintainer's Mac with nothing installed (measured). Code that only runs on the boards goes behind a thin hardware layer and is left out of the gate, with the reason written down. The Python tool and web page should use their languages' mainstream tools (Ruff, uv, pyright or Pyrefly and pytest-cov for Python; typed ESLint, Vitest and pnpm for the web page), gated on line and branch coverage, because neither stack has MC/DC. GitHub's cost limits matter most while the repo is private. GitHub Free includes **$12 of compute a month**, with no code scanning, no secret scanning, and (per the project's own notes) no enforced branch protection. So the private phase runs Linux checks on every pull request and the other two operating systems less often. Once public, almost every gap closes for free. For traceability, requirement IDs in test names plus a small Python checker are enough today, and they carry over to OpenFastTrace if the project outgrows them.

## MISRA C++:2023 sets the bar, and MISRA Compliance:2020 handles the exceptions

MISRA C++:2023 is the current edition. MISRA published it in **October 2023**. It targets **C++17**, is sold as a paid, "All rights reserved" document ([MISRA](https://misra.org.uk/misra-cpp2023-released-including-hardcopy/)), and takes in the AUTOSAR C++14 guidelines, though perhaps not every one of them ([Perforce, vendor](https://www.perforce.com/blog/qac/misra-cpp-2023-intro)). A MISRA working-group member counts **179 guidelines: 4 directives and 175 rules** ([all-about-industries, vendor author](https://www.all-about-industries.com/safety-critical-software-misra-c2023-from-a-to-z-a-b4e8def416835b51d1c27ca7607e14d8/)). MathWorks says 156 of them are decidable, meaning a tool can check them mechanically ([MathWorks, vendor](https://www.mathworks.com/help/bugfinder/ug/polyspace_coverage_coding_standard.html)). The open-source automotive project Eclipse S-CORE warns that using the standard with any C++ version other than C++17 "would mean that additional or different guidelines would need to be applied" ([Eclipse S-CORE](https://eclipse-score.github.io/score/main/contribute/development/cpp/coding_guidelines.html)). That warning matters for the UNO. The avr-gcc that ships with the Arduino AVR core is commonly said to be **version 7.3 [unverified]**, so its C++17 support needs checking before the project picks a language level.

Licensing decides how the standard can appear in an open repo. MISRA told its forum that a fully open-source tool may cite **only rule numbers**, not rule text ([MISRA forum](https://forum.misra.org.uk/showthread.php?tid=1626)), and cppcheck removed the rule texts from its repository for that reason ([cppcheck addons README](https://sources.debian.org/src/cppcheck/2.20.0-2/addons/README.md)). Zephyr shows the workable pattern: it lists each MISRA rule number with a short description in its own words, and lends contributors copies of the standard ([Zephyr coding guidelines](https://docs.zephyrproject.org/latest/contribute/coding_guidelines/index.html)). The same applies to AI agents. Their prompts and configs can carry rule IDs and the project's own summaries, never MISRA's wording.

The most useful MISRA document for this project is free. **MISRA Compliance:2020** defines Mandatory, Required and Advisory guidelines, a re-categorisation plan, deviation records and permits, a compliance summary, and **"adopted code"**: third-party libraries, drivers and the standard library, which may follow a separate, less strict plan as long as every violation is still reviewed ([MISRA Compliance:2020](https://misra.org.uk/app/uploads/2021/06/MISRA-Compliance-2020.pdf)). The Arduino core and ESP-IDF fit that definition exactly. The project's own code meets the standard strictly, the frameworks are declared as adopted code, and framework headers that cause warnings in project code get recorded deviations. The same document says compliance can only be claimed for a project with full evidence for every Mandatory and Required guideline ([MISRA Compliance:2020](https://misra.org.uk/app/uploads/2021/06/MISRA-Compliance-2020.pdf)). Without a qualified tool, that evidence doesn't exist, which is why "informed" is the honest label.

Open-source robotics is much less formal than this. PX4 and ArduPilot enforce style through formatters ([PX4](https://docs.px4.io/main/en/contribute/code.html), [ArduPilot](https://ardupilot.org/dev/docs/style-guide.html)). NASA F Prime requires CI to pass static analysis with no warnings ([F Prime](https://nasa.github.io/fprime/v3.1.0/UsersGuide/dev/code-style.html)). ROS 2's top quality level gives only "e.g. above 90%" line coverage as an example, with branch coverage optional ([REP 2004](https://raw.githubusercontent.com/ros-infrastructure/rep/master/rep-2004.rst)). Zephyr is the outlier: it requires a 147-rule subset of MISRA C:2012 for new code ([Zephyr](https://docs.zephyrproject.org/latest/contribute/coding_guidelines/index.html)). No regulation requires any of this for a toy-class robot. Adopting automotive rigour here is a choice made for learning and credibility, and the docs should say so.

The recommended stack has three layers. **clang-tidy** runs a curated profile: `bugprone`, `cert`, `cppcoreguidelines`, `misc`, `performance` and `portability`, minus checks that prove noisy (this profile is a starting point, **[unverified]** against real code). **Open-source cppcheck** runs with its built-in `avr8` platform for the UNO **[unverified]**. Both compilers run with warnings treated as errors. On top of these sits a **rule-mapping table** in the repo, which MISRA Compliance calls a Guideline Enforcement Plan ([MISRA Compliance:2020](https://misra.org.uk/app/uploads/2021/06/MISRA-Compliance-2020.pdf)). It lists each MISRA C++:2023 rule number, the check that approximates it (clang-tidy, cppcheck, a compiler warning, or code review), and a summary in our own words. The table doubles as the honest statement of the gap. MISRA's directives and process rules can only be checked by review, and nobody has published a benchmark of how many of the 179 guidelines this free combination covers. Writing the table needs a copy of the MISRA C++:2023 PDF.

Running these tools on cross-compiled code takes some setup. Clang-based tools need a `compile_commands.json` file for each target, plus the target's headers and macros. clang-tidy may reject GCC-only flags such as `-mmcu` or `-mlongcalls`, and mainline Clang has no Xtensa target, so the ESP32-S3 needs Espressif's `esp-clang` or approximate parsing. arduino-cli is said to produce the database with `--only-compilation-database`, and ESP-IDF writes one by default. All of these points come from established practice and are **[unverified]** in this research. The project should prove them in a spike before writing the gate. Analysis must also be limited to the project's own directories, or the Arduino core floods the output.

For Q2 ("no new findings"), the project's timing helps: there is no firmware yet. Instead of maintaining a baseline of known findings, the gate can be **zero findings from the first commit**. Every suppression is an inline comment carrying a deviation ID (for example `NOLINTNEXTLINE(check) DEV-003`). Each ID points to a row in a deviations file. A small Python check, runnable on all three operating systems, fails the build if any suppression lacks a known ID. Reusable exceptions, such as casting an integer address to a pointer for AVR register access, become deviation permits recorded as decision records. This matches MISRA Compliance's model ([MISRA Compliance:2020](https://misra.org.uk/app/uploads/2021/06/MISRA-Compliance-2020.pdf)) and the repo's "record what matters" rule. One rule needs stating explicitly: **only the maintainer approves a deviation**, because AI agents and contributors could otherwise silence a finding and justify it themselves. Tools that report only findings on changed lines, such as reviewdog or CodeChecker's diff mode, matter only if a baseline is ever needed **[unverified]**.

## 100% MC/DC is realistic only for logic that runs on the computer

Q3 is stricter than most of ISO 26262. Vendor summaries of ISO 26262-6, which is paywalled, rate unit-level MC/DC as highly recommended only at **ASIL D**, and branch coverage as highly recommended from ASIL B ([Verifysoft](https://www.verifysoft.com/en_ISO_26262_Road_Vehicles_Functional_Safety.html)). The table numbers and some of the ratings differ between sources ([Rapita](https://www.rapitasystems.com/iso26262), [LHPES](https://www.lhpes.com/blog/coverage-closure-metrics-field-defects)), so treat these as **[unverified]**. In aviation, DO-178C requires MC/DC only at Level A ([LDRA](https://ldra.com/ldra-blog/do-178c-structural-coverage-analysis/)). Q3 therefore matches the top integrity level at unit level. That is defensible as a deliberate choice, provided its scope is narrow and written down.

The compilers can do it. Clang added MC/DC with `-fcoverage-mcdc`, using the masking form of MC/DC ([Clang docs](https://clang.llvm.org/docs/SourceBasedCodeCoverage.html)). Clang 18 allowed at most **six conditions per decision** ([Clang 18 docs](https://prereleases.llvm.org/18.1.0/rc3/tools/clang/docs/SourceBasedCodeCoverage.html)), and the LLVM 19 cycle lifted that limit ([LLVM PR #95887](https://lists.llvm.org/pipermail/cfe-commits/Week-of-Mon-20240617/589423.html)). On the maintainer's Mac, **Apple Clang 21 instrumented a three-condition decision and reported 66.67% MC/DC**, and `llvm-cov export -summary-only` produced an `mcdc` total (measured, 8 Nov 2026). That run also showed two limits. `llvm-cov` has **no fail-under option**, and its LCOV export **drops MC/DC data**, so the gate needs a short script that reads the JSON summary, and services such as Codecov can't show MC/DC from it. GCC 14 added `-fcondition-coverage` (also masking MC/DC) ([arXiv 2501.02133](https://arxiv.org/abs/2501.02133v1), [gcov manual](https://gcc.gnu.org/onlinedocs/gcc/Invoking-Gcov.html)), and gcovr 8.7 added `--fail-under-condition` ([gcovr changelog](https://gcovr.com/en/latest/changelog.html)). Whether that flag checks MC/DC data or only decisions is **[unverified]**. GCC and Clang can disagree on MC/DC results for the same program ([GCC bug 115047](https://go.mail-archive.com/gcc-bugs@gcc.gnu.org/msg814395.html)), so the gate should use one compiler family.

| Option | Line and branch | MC/DC | Gate | Cross-platform cost |
|---|---|---|---|---|
| **Clang 19+ with llvm-cov** | Yes | Yes; tested on Apple Clang 21 (measured) | Script over the JSON summary | Nothing extra on macOS. Linux uses the distro's clang. **Windows MC/DC is [unverified]** |
| GCC 14+ with gcovr 8.7+ | Yes | Yes, through `-fcondition-coverage` | Built-in `--fail-under-*` flags ([gcovr](https://gcovr.com/en/latest/changelog.html)) | Real GCC on macOS means Homebrew `gcc`; Windows needs MinGW |

The recommendation is **Clang and llvm-cov** for the gate. The maintainer's Mac needs nothing new, and one compiler family keeps the results the same everywhere. The Windows job runs the tests but not the MC/DC gate until a CI run proves `-fcoverage-mcdc` works there.

The realistic scope is the **board-independent logic**: protocol encoding and decoding, state machines, fault monitors and diagnostic logic, calibration handling, and control maths. It is compiled for the computer from the same sources that avr-gcc compiles for the robot. Everything that touches registers, interrupts or the Arduino core sits behind small project-owned interfaces (GPIO, PWM, clock, serial). The board-side implementations of those interfaces are excluded from the gate **by directory, with the reason in a decision record**, and are checked by on-robot tests run with the maintainer's OK. This follows practitioner advice to keep hardware-in-the-loop tests few and unit-test everything else on the computer ([Interrupt](https://interrupt.memfault.com/blog/testing-vs-overhead)). It also mirrors DO-178C, which requires deactivated code to be justified ([LDRA](https://ldra.com/ldra-blog/do-178c-structural-coverage-analysis/)). A project-owned layer beats mocking `Arduino.h` with ArduinoFake, where a call nobody stubbed can crash the test ([ArduinoFake](https://github.com/arduhe/ArduinoFake)).

A 100% gate can also be met dishonestly, and four guardrails prevent it. First, Clang silently leaves out decisions over its limits (or, in Clang 18, decisions nested behind non-logical operators), only issuing a warning ([Clang docs](https://clang.llvm.org/docs/SourceBasedCodeCoverage.html)). Those warnings must fail the build. Second, templates that are never instantiated vanish from the report ([gcov manual](https://gcc.gnu.org/onlinedocs/gcc/Invoking-Gcov.html)), so tests must instantiate the types the firmware actually uses. Third, a project rule of **at most six conditions per decision** keeps any Clang version working and keeps the number of tests small. Fourth, reviewers check that tests assert results and don't merely execute lines, because 100% code coverage is not 100% test coverage ([Interrupt](https://interrupt.memfault.com/blog/testing-vs-overhead)).

For the test framework, GoogleTest 1.17 needs a C++17 compiler on the computer ([GoogleTest](https://github.com/google/googletest)), which every host compiler here provides, and it has the strongest mocking. Unity is the option for any test that must also run on the UNO ([PlatformIO](https://docs.platformio.org/en/latest/advanced/unit-testing/index.html)). A CMake and CTest build for the computer, next to the target build, keeps coverage flags under the project's control. Whether PlatformIO's own test runner supports coverage is **[unverified]**.

## Python and the web page get mainstream tools with a lighter coverage target

For the Python computer tool, the current mainstream stack is **Ruff** for linting, formatting and import sorting ([Ruff FAQ](https://docs.astral.sh/ruff/faq/)), **uv** with a committed `uv.lock` and `uv sync --locked` in CI, which fails if the lockfile is stale ([uv docs](https://docs.astral.sh/uv/concepts/projects/sync/)), and **pytest-cov** with `--cov-branch` and `--cov-fail-under` ([pytest-cov](https://pytest-cov.readthedocs.io/en/latest/config.html)). Ruff is not a type checker ([Ruff FAQ](https://docs.astral.sh/ruff/faq/)). For type checking, **pyright** leads the conformance snapshots at about 95 to 98%, Pyrefly reached a stable 1.0 in 2026 at about 88 to 92%, and ty is still a 0.x beta at about 53 to 71% ([Pyrefly comparison](https://pyrefly.org/blog/typing-conformance-comparison/), [pydevtools](https://pydevtools.com/handbook/explanation/how-do-mypy-pyright-and-ty-compare/), [Pyrefly 1.0](https://github.com/facebook/pyrefly/releases/tag/1.0.0)). Two of those snapshots come from sources friendly to Pyrefly. OpenAI announced in March 2026 that it is acquiring Astral, which makes uv, Ruff and ty ([SiliconANGLE](https://siliconangle.com/?p=735199)). The tools are permissively licensed, and choosing pyright or Pyrefly over ty avoids relying on that one vendor for everything.

For the web page, which arrives in stage 3, **ESLint with typescript-eslint's `strictTypeChecked`** config and `projectService` remains the most thorough type-aware linter ([typescript-eslint](https://typescript-eslint.io/getting-started/typed-linting/)). Biome and Oxlint are faster, but blog benchmarks disagree about how many type-aware rules they cover ([jsmanifest](https://jsmanifest.com/biome-oxlint-comparison-2026), [pkgpulse](https://www.pkgpulse.com/guides/oxc-vs-eslint-vs-biome-javascript-linting-2026)). **Vitest** can enforce coverage thresholds per metric, per file and per folder ([Vitest](https://vitest.dev/config/coverage)). **pnpm** blocks install scripts by default since version 10 and can delay newly published versions, a response to the 2025 npm attacks, which took about 2.5 and 12 hours to clean up ([pnpm](https://pnpm.io/blog/2025/12/05/newsroom-npm-supply-chain-security)). Both decisions can wait until the page is built.

Q5 says "the same discipline", but it can't mean MC/DC. pytest-cov and Vitest measure line and branch coverage ([pytest-cov](https://pytest-cov.readthedocs.io/en/latest/config.html), [Vitest](https://vitest.dev/config/coverage)), and this research found no MC/DC tool for either language. The consistent version is **100% line and branch coverage for logic modules** (decoders, recording index, compatibility checks), with user-interface glue excluded by path and the reason recorded, exactly as on the firmware side.

Supply-chain hygiene costs almost nothing. Since August 2025 GitHub can **enforce SHA-pinned actions** by policy ([GitHub changelog](https://github.blog/changelog/2025-08-15-github-actions-policy-now-supports-blocking-and-sha-pinning-actions/)). Actions lockfiles (`.github/workflows/actions.lock`) also pin the actions that other actions depend on, and they reached general availability on 28 October 2026, including on the Free plan. That comes from one news report ([InfoQ](https://infoq.com/news/2026/11/github-actions-lockfiles-ga)), so check GitHub's docs before relying on it. Dependabot is built into GitHub, while Renovate groups updates better ([Renovate](https://docs.renovatebot.com/bot-comparison/)). GitHub's dependency graph exports SPDX SBOMs ([GitHub](https://docs.github.com/en/code-security/supply-chain-security/understanding-your-software-supply-chain/exporting-a-software-bill-of-materials-for-your-repository)), and uv exports CycloneDX ([uv](https://docs.astral.sh/uv/concepts/projects/sync/)). REUSE puts an SPDX licence tag in every file ([REUSE](https://reuse.software/faq/)). It is worth adopting from the first code commit, because decision 0005 makes the whole history public later ([0005](../decisions/0005-publish-with-first-working-firmware.md)). The REUSE tool should run through `uvx` or pre-commit, not the global `pipx` install its FAQ suggests. The real private-phase gap is secrets. Secret scanning and push protection are **free only on public repos** for personal accounts ([GitHub](https://docs.github.com/en/code-security/secret-scanning/introduction/about-secret-scanning), [community answer](https://github.com/orgs/community/discussions/197712)). Until publication, a local scanner such as gitleaks, run in pre-commit and in CI, is the only protection for the Wi-Fi password. gitleaks was not researched here **[unverified]**. Scorecard's 18 checks and the OpenSSF Best Practices badge are free once the repo is public ([Scorecard](https://scorecard.dev/), [bestpractices.dev](https://bestpractices.dev/criteria)).

## Twelve dollars a month shapes CI until the repo goes public

GitHub Free includes **$12 of Actions compute a month** for private repos, expressed as money rather than minutes. Rates are **$0.006 a minute on Linux, $0.010 on Windows and $0.062 on macOS**. Usage stops when the money runs out unless a payment method is on file, so there is no surprise bill ([GitHub billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)). On public repos, standard runners are free ([GitHub billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)). Assuming a five-minute job (an estimate, not a measurement), one three-OS run costs about $0.39, of which $0.31 is macOS. That means about 30 full runs a month, or about 400 Linux-only runs. The private-phase pattern follows from that arithmetic. Every pull request gets a Linux job (build both firmware targets, run tests, enforce coverage, run static analysis) and skips it for docs-only changes. Windows runs on merges to main. macOS runs weekly or on demand, since the maintainer develops on a Mac and runs the same task-runner commands locally.

One gap has no free fix while the repo is private. The project's own notes say GitHub enforces branch protection on private repos **only on a paid plan**, which is why the repo uses a pre-push hook ([docs/tools.md](../tools.md)). Until publication, "CI must pass before merging" (Q4) depends on the maintainer's discipline. That is acceptable while the maintainer is the only person merging, and it should be written down as a known gap rather than implied. Third-party coverage and quality services (Codecov, SonarQube Cloud) aren't needed: a job summary and a failing exit code enforce the gate without another account. Codecov's free plan does cover private single-user repos up to 250 uploads a month ([Codecov](https://about.codecov.io/pricing/)).

Going public changes almost everything at once, and the project should prepare the configuration in advance so it can be switched on the same day. That means the three-OS matrix on every pull request, **CodeQL default setup** (which analyses C/C++ without a build) ([GitHub](https://docs.github.com/en/code-security/code-scanning/enabling-code-scanning/configuring-default-setup-for-code-scanning)), SARIF uploads from cppcheck and clang-tidy, secret scanning with push protection, the prepared branch ruleset, Scorecard, and the PVS-Studio and Cppcheck Premium enquiries. A runner attached to the robot needs care. Self-hosted runners are free today, since the planned charge was postponed ([GitHub changelog](https://github.blog/changelog/2025-12-16-coming-soon-simpler-pricing-and-a-better-experience-for-github-actions/)), but a pull request from a fork once gave researchers root on PyTorch's self-hosted runners ([DevClass](https://devclass.com/2024/01/15/spotlight-on-github-self-hosted-runners-again-as-researcher-demonstrates-attack-on-pytorch-code)). A robot runner must never run on `pull_request` triggers. It should run only after manual approval through a protected environment, which also enforces the "don't run its motors without the maintainer's OK" rule.

| Secrets | Local scanner in pre-commit and CI | Plus GitHub secret scanning and push protection |
| Dependencies | Dependabot; SHA pins or actions lockfile | Same, plus Scorecard and Best Practices badge |
| Hardware-in-the-loop | Manual, by the maintainer | Self-hosted runner only behind an approval gate, never on fork PRs |

## Requirement IDs in test names are enough traceability for now

The open-source traceability tools are all maintained, and all of them are heavier than the project needs today. **OpenFastTrace** fits Q6 best on paper. Its requirements are written in Markdown, and tags in code and tests in any language mark what covers them. Version 4.10.0 came out in September 2026, it is GPL-3.0, and it needs Java 17 ([OpenFastTrace](https://github.com/itsallcode/openfasttrace), [releases](https://github.com/itsallcode/openfasttrace/releases)). Doorstop stores one Markdown file per item ([Doorstop](https://doorstop.readthedocs.io/en/latest/about/changelog.html)). StrictDoc's Markdown and test-report links are still experimental ([StrictDoc](https://strictdoc.readthedocs.io/en/latest/latest/docs/strictdoc_01_user_guide.html)). sphinx-needs needs a Sphinx documentation site ([sphinx-needs](https://sphinx-needs.readthedocs.io/en/latest/)). BASIL is a server aimed at ISO 26262 audits ([ELISA](https://elisa.tech/ambassadors/2026/04/01/elisa-seminar-recap-notes-from-requirements-to-code-managing-end-to-end-traceability-with-basil/)).

The requirements already have stable IDs (S3, D11, Q1 and so on) in `docs/requirements.md`. The cheapest approach that fully meets Q6 puts those IDs in test names or markers (for example a GoogleTest suite named after the ID, or `@pytest.mark.req("S3")`), adds a "Requirements" field to the pull request template, and runs a short Python checker in CI. The checker lists requirements with no test and fails on IDs that don't exist. It adds no runtime, AI agents can follow it easily, and the IDs carry over to OpenFastTrace if the project needs its reports later. OFT's own CI wrapper is a bash script ([OpenFastTrace](https://github.com/itsallcode/openfasttrace)), so a move to OFT would call the JAR from the project's task runner instead.

| Requirement | Recommended gate | Tools | Gap stated honestly |
|---|---|---|---|
| Q1 | MISRA C++:2023-informed: rule-mapping table, CERT C++ for ESP32 network code, Power of Ten as minimum | clang-tidy, cppcheck, compiler warnings, review | No free tool checks MISRA C++:2023; no compliance claim; AVR C++ level unverified |
| Q2 | Zero findings from the first commit; every suppression carries a deviation ID approved by the maintainer | Python suppression check; deviations file and permits | Only as strong as the rules the tools check |
| Q3 | 100% line, branch and MC/DC for board-independent logic on the computer | Clang 19+ and llvm-cov, script on JSON summary, GoogleTest | Board code excluded and tested by hand; Windows MC/DC unverified |
| Q4 | Required jobs on every PR | GitHub Actions, task runner | Not enforced by GitHub until public |
| Q5 | Lint, format, type check, 100% line and branch for logic modules | Ruff, uv, pyright or Pyrefly, pytest-cov; later ESLint, Vitest, pnpm | No MC/DC for Python or TypeScript |
| Q6 | Requirement IDs in tests and PRs, checked by script | Python checker; OpenFastTrace later | Shows which tests exist for a requirement, not that they are sufficient |

## Decisions for the maintainer

1. **Claim level for Q1:** "MISRA C++:2023-informed" with a public rule-mapping table, or pay for a qualified tool so the project can claim compliance. The mapping table needs a copy of the MISRA C++:2023 PDF. Decide whether to buy one.
2. **C++ language level per board:** confirm which avr-gcc version the `arduino:avr` 1.8.8 core ships and how much C++17 it supports, then choose C++17 (the version MISRA C++:2023 assumes) or record the deviations an older level needs.
3. **Supplementary standards:** whether CERT C++ applies to all ESP32-S3 network and parsing code, and whether Power of Ten's no-allocation-after-start-up rule becomes a project rule on both boards.
4. **Q2 deviation process:** where deviation records and permits live (a deviations file plus decision records is suggested), and confirming that only the maintainer can approve one, never a contributor or an AI agent.
5. **Q3 scope:** which directories count as unit-tested logic, the list of excluded hardware-layer files and why, and whether to adopt the six-condition limit per decision.
6. **Coverage toolchain:** Clang and llvm-cov (recommended), or GCC and gcovr. Also whether Windows CI must prove MC/DC before the gate counts there.
7. **Host test setup:** GoogleTest with CMake and CTest (recommended), or PlatformIO with doctest or Unity, and how the framework version is pinned.
8. **Q5 targets:** 100% line and branch for Python logic modules or a lower number; pyright or Pyrefly as type checker; and, when stage 3 arrives, typed ESLint or Biome.
9. **Private-phase CI shape:** accept Linux-on-every-PR with less frequent Windows and macOS runs, and record that GitHub won't enforce merge gates until publication. The alternative is paying for a plan that does.
10. **Supply chain:** SHA pins or the new actions lockfile; Dependabot or Renovate; adding a local secret scanner (and listing it in `docs/tools.md`); and REUSE headers from the first code commit.
11. **Q6 strength:** report-only (list requirements without tests) or blocking (every requirement in the current stage must have at least one test), and whether to move to OpenFastTrace later, which needs Java.
12. **Publication-day checklist:** which items from the "once public" column to switch on immediately, and whether to apply for PVS-Studio and ask Cppcheck about a Premium licence.
13. **Hardware-in-the-loop CI:** whether a robot runner is ever wanted, and if so, that it runs only after manual approval and never on fork pull requests.

## Conclusion

Q3 is the requirement that looks most automotive, but Q1 is the one most likely to be overstated. Free tools can prove 100% MC/DC on a well-isolated logic layer with stronger evidence than many commercial projects produce. They cannot prove MISRA C++:2023 compliance at all, so the project's credibility depends on saying "informed" and publishing the rule-mapping table that shows the difference. The architecture has the most influence on test quality: a thin, owned hardware layer is what makes the coverage gate meaningful, the static analysis clean, and the robot safe to test without touching it.

The timing favours strictness. Starting from zero lines of firmware, a zero-findings and full-coverage gate costs nothing to adopt and only gets more expensive to add later. Since decision 0005 publishes the whole history, every early commit will eventually be judged by public standards. The private phase is therefore when to build the discipline locally and prepare the public configuration, so that going public mostly means switching on free GitHub features that are already configured.
