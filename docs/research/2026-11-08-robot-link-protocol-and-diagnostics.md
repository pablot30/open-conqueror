# R2: Robot link protocol and diagnostics

**Background research from 8 November 2026, written before [decision 0006](../decisions/0006-walking-skeleton-first.md) cut stage 2 back to a walking skeleton.** Its recommendations are input, not decisions. Where a decision or the [architecture](../architecture.md) says otherwise, they win.

**In one line:** Describe the link once, generate everything else.

Research date: 8 November 2026. Sources are cited inline. **[unverified]** marks anything that was not confirmed against a primary source during this research. Figures marked **estimate** are design arithmetic, not measurements. Nothing in this report was built, flashed or measured on the robot.

The robot should use **one small binary protocol, defined once in a project-owned YAML description file**. A Python generator turns that file into C++ for both boards, Python for the computer tool and TypeScript for the web page, and it can also export DBC, A2L and ODX. Building our own is the main path, not a fallback. No open format covers signals, calibration and diagnostics together, the only official DBC document carries a no-redistribution notice, and the A2L and ODX specs are paid. Each frame is a short packet: a message ID, a sequence number, at most 32 bytes of payload, and a CRC-16 seeded per message the way MAVLink's CRC_EXTRA is. The packet sits inside a delimiter-based envelope. That envelope is COBS on a raw UART or USB, and **Base64 between braces during stage 2**, because the stock camera firmware's bridge only passes text in `{…}` at 9600 baud. Safety doesn't depend on delivery. The UNO stops by itself after 300 ms without a valid frame, stops are repeated rather than retried, and only commands get acknowledgements. Logs are tokens defined in the same description, so no log strings live on the UNO. The computer tool records MCAP files with session metadata, with the description attached so each file decodes on its own, and it serves the same stream live to open-source viewers such as Lichtblick. Calibration and fault codes share one request/response service shaped like a small subset of UDS. Changes go to RAM working values. An explicit store writes them to A/B EEPROM slots that carry a CRC and a schema hash. A fault memory uses the ISO 14229 status byte with small snapshots. The estimated cost on the UNO is **4.5 to 9.5 KB of flash and 350 to 520 bytes of RAM**, which fits T8 on paper. None of it has been built, and several facts about the bridge, baud rates and tools still need checking.

## The recommended design stacks six thin layers on two legs

The design keeps the same packet from end to end and changes only what's underneath it. The UNO speaks one compact packet format. The ESP32-S3 reads packet headers so it can prioritise and enforce safety, and passes payloads through unchanged. The computer tool and the browser decode payloads with code generated from the same description. That way each message has one definition, not one per hop.

```
              UNO (ATmega328P)          ESP32-S3                        Computer tool / browser
Tools         -                         -                               record MCAP, view live, plot, replay,
                                                                        calibrate, read and clear fault codes
Services      telemetry, log tokens,    the same services for its own   generated decoders
              calibration, fault codes, data, plus a gateway that       (Python, TypeScript)
              hello, time sync          routes requests to the UNO
Messages      packed structs generated from one YAML description: scaled integers, no floats on the UNO
Packet        [message ID][sequence][route]  payload <= 32 B  [CRC-16 seeded per message]
Envelope      COBS + 0x00 on UART and USB   |   "{" Base64 "}" through the stock bridge (stage 2 only)
Wire          UART at 9600 (stock bridge), then 250k or 500k (stage 3)  |  Wi-Fi: UDP to the tool, WebSocket to the browser
```

The two legs change between stages, because decision 0004 keeps the stock camera firmware running until stage 3 ([0004](../decisions/0004-own-protocol-and-control-page.md)).

| Leg | Stage 2 (stock camera firmware) | Stage 3 (our camera firmware) |
|---|---|---|
| UNO to camera board | 9600 baud, text frames in braces, Base64 envelope | 250k or 500k baud, COBS envelope |
| UNO to computer over USB (Upload position) | Any baud the USB chip supports, COBS envelope | Same, for bench work |
| Camera board to computer | Stock TCP bridge on port 100. The tool must answer `{Heartbeat}` | UDP datagrams, one packet per datagram |
| Camera board to browser | Not possible: browsers can't open raw TCP | WebSocket served by our firmware |

The rest of this report justifies each layer. It also says where the evidence is thin, and what the maintainer has to decide.

## The stock bridge forces text frames at 9600 baud until stage 3

During stage 2 the Wi-Fi path runs through ELEGOO's bridge. That bridge only forwards **text inside `{` and `}` at 9600 baud**, removes spaces, and forwards everything else unchanged. It drops a client that misses `{Heartbeat}` replies, and sends `{"N":100}` to the UNO when a client disconnects ([camera board](../hardware/camera-board.md#working-with-the-stock-bridge)). A raw binary frame would break this the first time a payload byte happened to equal `}`. The fix is to treat braces as the delimiter and Base64 as the stuffing. The standard Base64 alphabet has no braces, spaces, quotes or colons ([RFC 4648](https://datatracker.ietf.org/doc/html/rfc4648)), so a receiver resynchronises at the next `{`. It can also tell the bridge's own `{"N":100}` from our frames by the quote character, and must treat that frame as a stop. Junk such as the factory-test frames `{Factory}` and `{WA_NO}` ([camera board](../hardware/camera-board.md)) fails Base64 decoding or the CRC and is dropped. Base64 costs about **4/3 of the binary size**, which is the same ratio pw_tokenizer gives for its text-channel mode ([pw_tokenizer](https://pigweed.dev/pw_tokenizer/tokenization.html)).

On a raw byte stream, **COBS is the strongest framing for short frames**. It adds at least 1 and at most ⌈n/254⌉ bytes, removes every 0x00 so that a single 0x00 ends the frame, and lets a receiver recover from a bad packet by waiting for the next delimiter ([Wikipedia: COBS](https://en.wikipedia.org/wiki/Consistent_Overhead_Byte_Stuffing)). For frames of 254 bytes or less, the overhead is always exactly one code byte plus the delimiter. Worst case and typical case are the same, which suits a link with a stop deadline.

| Framing | Overhead | Resync after a lost byte | Fit here |
|---|---|---|---|
| COBS | +1 byte per 254, plus the 0x00 delimiter ([Wikipedia](https://en.wikipedia.org/wiki/Consistent_Overhead_Byte_Stuffing)) | At the next 0x00 | **UART and USB, stage 3 onward** |
| COBS/R | 0 to +1 byte; the decoder must accept a code longer than the remaining bytes ([COBS/R](https://pythonhosted.org/cobs/cobsr-intro.html)) | Same as COBS | Saves one byte, adds a special case. Not worth it |
| HDLC or SLIP escaping | Under 1% on average, but can double the frame ([Wikipedia](https://en.wikipedia.org/wiki/Consistent_Overhead_Byte_Stuffing)) | At the next flag byte | Worst case breaks the timing budget |
| Sync byte plus length (MAVLink, eRPC) | Lowest. MAVLink rescans after a CRC failure, and eRPC's documented framing has no sync byte or resync step ([MAVLink](https://mavlink.io/en/guide/serialization.html), [eRPC](https://embeddedrpc.github.io/eRPC/classerpc_1_1_framed_transport.html)) | Can lock onto a false sync byte inside a payload | Not on a noisy UART |
| Base64 in braces | +33%, plus 2 bytes | At the next `{` | **Stage 2, through the stock bridge** |

Real protocols in this class protect each frame with a **16-bit CRC**. MAVLink uses CRC-16/MCRF4XX over everything except the start byte, and folds in a per-message CRC_EXTRA byte ([MAVLink](https://mavlink.io/en/guide/serialization.html)). eRPC uses CRC-16 on both header and body ([eRPC](https://embeddedrpc.github.io/eRPC/classerpc_1_1_framed_transport.html)). The cheapest choice for us is CRC-16 with the 0x1021 polynomial. Python's standard library already computes it as `binascii.crc_hqx` ([Python docs](https://docs.python.org/3/library/binascii.html)), so the computer tool needs no extra package. avr-libc's `_crc_xmodem_update` is believed to be the matching table-free AVR routine, but that page returned errors during research, so its exact variant is **[unverified]** and needs a shared test vector. Cycle cost isn't a concern either way. At 115200 baud a byte arrives every 87 µs, about 1,390 CPU cycles, so even a slow bitwise CRC takes a small fraction of each byte's time (an inference; the only published AVR CRC benchmark contradicts itself ([industrialmonitordirect](https://industrialmonitordirect.com/blogs/knowledgebase/modbus-crc16-implementations-for-atmega128-algorithm-verification))). Firmware images need a whole-image CRC-32 or hash on top of this, but that belongs to the update design.

The baud rate for stage 3 should be an **exact divisor of 16 MHz**. Using the ATmega328P's formulas, 57600 is only usable with double-speed mode (−0.79%), and 115200 is +2.12% or −3.55%, which is marginal against the usual ±2% combined error budget. **250k, 500k and 1M are exact** (computed from the datasheet formulas, not read from its tables ([Microchip](https://www.microchip.com/en-us/product/atmega328p))).

| Baud | Error at 16 MHz | Byte time | Cycles per byte | 64-byte ring holds |
|---|---|---|---|---|
| 9600 | +0.16% | 1.04 ms | ~16,700 | 67 ms |
| 115200 | +2.12% (U2X) | 87 µs | ~1,390 | 5.6 ms |
| 250000 | 0.00% | 40 µs | 640 | 2.6 ms |
| 500000 | 0.00% | 20 µs | 320 | 1.3 ms |
| 1000000 | 0.00% | 10 µs | 160 | 0.64 ms |

At 1M baud, any interrupt or critical section longer than about 10 to 20 µs risks an overrun, because the AVR's UART buffers only two bytes in hardware (an inference from the byte times above). So **250k is the safe default and 500k the stretch**. Two facts still need checking: whether the ESP32-S3's UART divides these rates cleanly, and whether the UNO's CH340 USB chip supports them for bench work. Both are **[unverified]**. Faster edges also make the open question about the UNO's 5 V TX driving GPIO3 more pressing. The pin's limit is VDD + 0.3 V, about 3.6 V, and nothing sits between them ([camera board](../hardware/camera-board.md#5-v-on-the-uart)). That measurement should come before choosing a stage 3 baud rate. The Arduino core's default rings are **64 bytes each for RX and TX**, and can be resized with a `#define` ([HardwareSerial.h](https://raw.githubusercontent.com/arduino/ArduinoCore-avr/master/cores/arduino/HardwareSerial.h)).

## Safety rests on the UNO's own 300 ms timer, not on the network

The surveyed protocols all put reliability at the application layer, on top of an unreliable transport. MAVLink gives every packet a one-byte sequence number but has no transport-level ack. Acks exist only for particular services ([MAVLink](https://mavlink.io/en/guide/serialization.html)). The robot should follow the same pattern. The tool sends a drive command or heartbeat 10 to 20 times a second, and **the UNO stops if no valid frame arrives for 300 ms**, which meets S3 without trusting anything upstream. Commands carry a sequence number and get an ack with a result code, with at most one or two retries. A stop is idempotent, so it is sent several times in a row instead of waiting for an ack. Telemetry and logs are never acked and are allowed to drop. The stock bridge can't provide S3 for us. It drops a client only after more than three missed heartbeats at one per second ([camera board](../hardware/camera-board.md)), which takes ten times longer than S3 allows. Its `{"N":100}` is a useful backup, but the UNO's timer is the safety mechanism.

The UART is full duplex, so telemetry from the UNO never delays a command going to it. The only wait a stop can suffer on the wire is behind another host-to-UNO frame that has already started. That is why payloads are capped at 32 bytes, and why calibration writes carry one parameter per frame. The table below estimates the stop path for each leg, using a 3-byte header and a 2-byte CRC.

| Path | Stop frame on the wire | Worst wait behind another frame | Network part | Verdict (**estimate**) |
|---|---|---|---|---|
| USB at 250k (stage 2 bench) | under 1 ms | about 1.5 ms behind a full 32-byte frame | none | Easily inside S1 and T7 |
| Stock bridge at 9600, Base64 | about 10 ms (10 bytes) | about 56 ms behind a full frame, or about 15 ms behind a drive command | Wi-Fi plus TCP, **unmeasured** | S1 holds if Wi-Fi plus bridge stays under about 80 ms. **T7's 50 ms typical is tight** |
| Our firmware, 250k UART, UDP | under 1 ms | about 1.5 ms | Wi-Fi UDP, **unmeasured** | Likely inside both |
| Browser over WebSocket | under 1 ms | about 1.5 ms | TCP can stall behind a lost segment | The 300 ms timer is the backstop |

At 9600 baud the link carries only about 960 bytes a second each way. That still leaves room for T7's rate (**estimate**). A telemetry packet with a 24-byte payload becomes 42 bytes once encoded, so 10 Hz uses about 44% of the UNO's transmit side. That leaves about 540 bytes a second for logs and replies. A 14-byte drive command at 20 Hz uses about 29% of the receive side.

On the Wi-Fi leg, the drone world's answer is **one protocol frame per UDP datagram**. DroneBridge-style ESP32 bridges broadcast MAVLink to UDP port 14550, after the ground station sends one packet to register ([PX4 docs](https://docs.px4.io/v1.16/en/telemetry/esp32_wifi_module.html)). UDP has no head-of-line blocking, so a late telemetry packet never holds up a stop, and it suits the desktop tool. Browsers can't open raw UDP sockets. They can use unordered, no-retransmit WebRTC data channels ([web.dev](https://web.dev/articles/webrtc-datachannels), [RFC 8831](https://datatracker.ietf.org/doc/html/rfc8831)), and WebTransport became Baseline when Safari 26.4 shipped it in March 2026 ([WebRTC.ventures](https://webrtc.ventures/2026/04/webtransport-is-now-baseline-what-it-means-for-real-time-media/), [WebKit](https://webkit.org/?p=17862)). Both need DTLS or QUIC stacks on the device, and no source showed either running on an ESP32-S3. **WebSocket is the pragmatic browser transport**, with the 300 ms timeout covering its stalls. Foxglove's maintainers now say not to implement their WebSocket protocol on your own server ([Foxglove ws-protocol](https://github.com/foxglove/ws-protocol/blob/main/docs/spec.md)). Foxglove compatibility therefore belongs in the computer tool, not on the ESP32.

| Bridge style (stage 3) | What the ESP32 does | Gains | Costs |
|---|---|---|---|
| Transparent | Copies bytes between UART and socket, like DroneBridge and mavp2p ([PX4 docs](https://docs.px4.io/v1.16/en/telemetry/esp32_wifi_module.html), [mavp2p](https://github.com/gswly/mavp2p)) | Simplest firmware | Can't put a stop ahead of queued traffic, or stop the UNO when Wi-Fi goes quiet |
| **Frame-aware (recommended)** | Reads the header, gives stops a priority queue, sends a stop when Wi-Fi heartbeats end, routes by the route byte, adds its own messages | Safety and priority without a second protocol definition | Header parsing and COBS on the ESP32 |
| Terminating | Decodes everything and re-encodes, for example JSON for the browser | Friendliest format for the browser | Two protocol definitions to keep in step |

## Generated packed structs from our own YAML beat every off-the-shelf format

On a 2 KB part, **packed C structs generated from a description** are the only serialization with headroom. The alternatives either don't fit or cost bytes on the wire that a 9600-baud link can't spare.

| Format | Cost on the UNO | Verdict |
|---|---|---|
| Generated packed structs | Smallest; fixed sizes; unmeasured | **Recommended** |
| MAVLink v2 | Minimum frame 12 bytes, maximum 280 ([MAVLink](https://mavlink.io/en/guide/serialization.html)). The standard receive buffer holds a full frame, about 290 bytes **[unverified]**. Copter dropped the 8 KB-RAM ATmega2560 boards after 3.2.1 ([ArduPilot](https://ardupilot.org/copter/docs/common-apm25-and-26-overview.html)) | Copy its ideas, not the protocol |
| nanopb | 5 to 20 KB of flash and about 1 KB of stack, plus message structs ([nanopb](https://jpa.kapsi.fi/nanopb/docs/)) | Too big |
| zcbor, MPack | Low footprint claimed, no numbers published ([zcbor](https://github.com/NordicSemiconductor/zcbor), [MPack](https://github.com/ludocode/mpack/)); field tags cost wire bytes | Not on the UNO |
| micro-ROS | Needs "tens of kilobytes of RAM" and doesn't support the UNO ([micro-ROS](https://micro.ros.org/docs/overview/hardware), via search; [ROS Answers](https://answers.ros.org/question/416049/)) | No |

D13 asks for signals, calibration and diagnostics each to be described once, as DBC, A2L and ODX do in cars. The research found **no open format, and no open tool, that covers all three**. The calibration side (XCP, A2L) and the diagnostics side (ODX, UDS) live in separate toolchains ([XCPlite](https://github.com/vectorgrp/XCPlite), [odxtools, an open-source ODX library](https://pypi.org/project/odxtools/)). The options for the project's source of truth compare like this.

| Source format | Openness | Code generation | Calibration and diagnostics | Industry tools | Main cost |
|---|---|---|---|---|---|
| DBC | No open spec. Vector's v1.0.5 document forbids redistribution ([copy](https://rust-digger.code-maven.com/src/rrdbc-0.1.0/dbc/dbc-file-format-documentation_compress.pdf)) | cantools 45.1.2 (MIT, Oct 2026) generates C with a no-float option ([cantools](https://github.com/cantools/cantools)) | No natural place; custom attributes only | Read natively | Hits a ceiling quickly; CAN-shaped IDs and lengths |
| ARXML | AUTOSAR specs are free downloads (terms **[unverified]**) | autosar-data reads and writes it (Apache-2.0/MIT) ([autosar-data](https://github.com/DanielT/autosar-data)) | Possible, but verbose | Read natively | Long chains of cross-referenced elements; impractical to edit by hand |
| MAVLink XML + mavgen | Definitions and generated C are MIT; the generator is LGPLv3 ([MAVLink](https://mavlink.io/en/#supported_languages)) | C, Python, TypeScript and more | Parameters yes; no units, factors or offsets | None | Adopts MAVLink's framing overhead |
| Cyphal DSDL + Nunavut | MIT ([Nunavut](https://github.com/OpenCyphal/nunavut)) | C11 and Python; avr-gcc support **[unverified]** | Signals only | None | No units, no exporters |
| **Own YAML + Python generator** | Ours, Apache-2.0 | Whatever we template: AVR C++, ESP32 C++, Python, TypeScript | **All three in one file** | Through exporters | We maintain the generator and its schema |

**Designing our own is the recommended option**, and it's the pattern MAVLink (XML plus mavgen) and Cyphal (DSDL plus Nunavut) already follow. The file holds message definitions with DBC-like signal semantics (type, factor, offset, unit, range), calibration parameters with stable numeric IDs, defaults and limits, fault codes with their snapshot fields, and log events. A JSON Schema checks the YAML in CI, and Jinja templates emit the code. The cost is real. By the author's **estimate** it is the largest piece of tooling in stage 2, roughly 1,500 to 3,000 lines of Python, templates and tests. The generated C++ also falls under the earlier quality gates, so it must pass clang-tidy and cppcheck cleanly, and the protocol logic it produces must reach full coverage in host tests like any other board-independent code. Generated code isn't exempt. The avr-gcc 7.3 toolchain in the Arduino core defaults to `-std=gnu++11` and accepts `-std=gnu++17`, but it has no standard library ([Arduino forum](https://forum.arduino.cc/t/which-version-of-c-is-currently-supported/1285868), [toolchain-avr](https://uithub.com/arduino/toolchain-avr)). The templates must therefore avoid the STL.

Exports to industry formats can come later and stay cheap, because good open writers exist. **DBC**: cantools writes DBC, and canmatrix converts YAML or JSON matrices to DBC with `canconvert` ([cantools releases](https://api.github.com/repos/cantools/cantools/releases?per_page=3), [canmatrix](https://github.com/ebroecker/canmatrix)). Our 32-byte payloads fit CAN FD's 64-byte limit. **A2L**: pyA2L has a Creator API (LGPL-3.0+, fine as a development-time tool) ([pyA2L](https://pya2l.readthedocs.io/_/downloads/en/latest/pdf/)). a2ltool (MIT/Apache-2.0) can create A2L from an ELF, though it has no prebuilt macOS binary, and how it handles AVR debug information is untested ([a2ltool](https://github.com/DanielT/a2ltool)). An exported A2L's addresses mean nothing to a tool unless the robot also speaks XCP, so it would serve as documentation, not as a working tool link. **ODX**: odxtools, an open-source ODX library, decodes and compares ODX databases, but the pages read during research didn't confirm that it can write PDX files ([odxtools](https://pypi.org/project/odxtools/)). The ASAM MCD-2 MC (A2L) spec is free only to ASAM members ([ASAM](https://www.asam.net/standards/detail/mcd-2-mc/)). Exporters should therefore follow what the open tools accept, not a reading of the paid spec.

D13's own check is to add a signal and see it in the tool without writing code. That works if the computer tool loads the description at run time, or regenerates its decoders as part of the build. It also needs every MCAP channel's schema to come from the same file. D15's compatibility checks reuse MAVLink's best idea. **CRC_EXTRA** is a hash of each message's name, field types, names and array lengths, folded to 8 bits and mixed into the frame CRC. Mismatched definitions then fail the checksum instead of decoding garbage. Extension fields are left out of the hash, so fields can be appended without breaking older receivers ([MAVLink](https://mavlink.io/en/guide/serialization.html)). On top of that, the firmware embeds the first 4 bytes of a SHA-256 of the normalised description. It reports them in a HELLO reply along with firmware version, protocol version, maximum frame size and capability bits, much as Foxglove servers announce capabilities on connect ([Foxglove ws-protocol](https://github.com/foxglove/ws-protocol/blob/main/docs/spec.md)). The tool refuses to drive a robot whose hash it doesn't know. Calibration sets carry the same hash, so the UNO refuses a set made for another release. Optiboot can't check anything, so for firmware images the check has to sit in the flashing tool.

## Logs shrink to tokens, and recordings carry their own decoder

Every serious small-MCU logging system uses the same trick. At build time each format string becomes a small ID, the strings stay on the computer, and the device sends only the ID and raw binary arguments. Trice keeps a `til.json` dictionary and needs "just four bytes" for a bare record ([Trice](https://rokath.github.io/trice/docs/TriceUserManual.html)). pw_tokenizer hashes strings to 32-bit tokens and reports firmware images shrinking by up to 18% ([pw_tokenizer](https://pigweed.dev/pw_tokenizer/tokenization.html)). Zephyr refers to strings by their ELF address ([Zephyr](https://docs.zephyrproject.org/latest/services/logging/index.html)), and defmt sends table indices ([defmt](https://defmt.ferrous-systems.com/)). None of them is documented on AVR. Zephyr has no AVR port ([Zephyr](https://docs.zephyrproject.org/latest/introduction/index.html)), and the Arduino logging libraries found still format text on the device ([AvrArdLogging](https://github.com/felixstorm/AvrArdLogging), [Arduino-Log](https://github.com/Iv/Arduino-Log)). Trice is plain C, MIT-licensed and heap-free, so it is the most plausible ready-made option, but it publishes no footprint figures and has no AVR example ([Trice](https://github.com/rokath/trice)).

For the UNO the better fit is to **declare log events in the description file**, for example `battery_low: {level: warn, text: "Battery {mv} mV", args: {mv: u16}}`. The generator then emits a typed `log_battery_low(mv)` function plus the dictionary. No source scanner is needed, the strings never reach RAM or flash, and the log message type is just another packet. It is less convenient than printf-style logging, and that is the honest cost. A short Trice spike measured with `avr-size` is the alternative, if the maintainer prefers ad-hoc log lines. The ESP32-S3 has room to send text logs, so tokens are only essential on the UNO. Telemetry uses the same machinery. Periodic messages carry scaled integers defined in the description, the rate of each is itself a calibration parameter (D7's "rate we can choose"), and the computer applies factor, offset and unit.

**MCAP is the right recording format.** Its chunks are compressed with zstd or lz4, and every file carries a chunk index with time ranges, which covers D14's "chunks with an index". It has key/value Metadata records and Attachments with their own CRC32, timestamps in nanoseconds since an epoch you choose, and separate `log_time` and `publish_time` fields ([MCAP spec](https://mcap.dev/spec)). It is MIT-licensed, with libraries in C++, Python, TypeScript, Rust, Go and Swift, and a CLI that merges and splits files ([mcap](https://github.com/foxglove/mcap)). ROS 2 made it the default bag format in Iron, partly so that tools outside ROS could read bags ([rosbag2](https://github.com/ros2/rosbag2/blob/master/README.md)). Each recording should hold a `session` Metadata record with date, robot ID, both boards' git SHAs, calibration-set ID, purpose and operator. It should also attach the description file, the log dictionary and the calibration set, so it decodes years later without the repo, and record a channel of raw link packets next to the decoded channels, so it can be re-decoded if a decoder bug turns up. For analysis across sessions, a short script converts each MCAP to Parquet. Parquet writes its metadata in a footer at the end, so it suits batch analysis, not live recording ([Parquet](https://parquet.apache.org/docs/file-format/)). DuckDB or Polars can then query every session at once. Community tools already do this conversion, but they're young enough that a 50-line script is safer ([rosbag-resurrector](https://pypi.org/project/rosbag-resurrector/), [hephaes](https://pypi.org/project/hephaes/0.2.1/)).

| Format | Live append | Index and context | Openness | Fit |
|---|---|---|---|---|
| **MCAP** | Yes, chunked | Chunk index, Metadata, Attachments ([spec](https://mcap.dev/spec)) | MIT | **Recording** |
| **Parquet** | No, footer written last ([Parquet](https://parquet.apache.org/docs/file-format/)) | Column statistics | Apache | **Cross-session analysis** |
| ASAM MDF4 (4.3.0, Sept 2025) | Yes | Rich, automotive-native | Spec free to view online, otherwise paid or member-only ([ASAM](https://www.asam.net/standards/detail/mdf/)); asammdf is LGPLv3+ ([asammdf](https://github.com/danielhrisca/asammdf)) | Only if automotive tools are needed |
| HDF5 with SWMR | Yes, with strict limits: no new objects or strings while writing ([HDF Group](https://support.hdfgroup.org/documentation/hdf5/latest/_s_w_m_r.html)) | Hierarchical | BSD-style | Awkward for mixed logs |

The cleanest way to record and stream live at the same time is the **Foxglove SDK** (MIT; Python, C++, Rust). One script opens an MCAP sink and a local WebSocket server, and every `log()` call goes to both ([Foxglove SDK](https://docs.foxglove.dev/docs/sdk/example)). The computer tool would own the serial or Wi-Fi link, decode packets, stamp receive times and publish through the SDK. The MCAP file is the contract, and the viewers are replaceable.

| Foxglove | Closed source since March 2024 ([Foxglove](https://foxglove.dev/blog/foxglove-2-0-unifying-robotics-observability)) | Desktop app, sign-in on first launch ([ROS Discourse](https://discourse.openrobotics.org/t/foxglove-2-0-integrated-ui-new-pricing-and-open-source-changes/36583)) | Free tier: 3 users, 5 devices, 10 GB ([pricing](https://foxglove.dev/pricing)) |
| Teleplot | MIT ([GitHub](https://github.com/nesnes/teleplot)) | Runs anywhere | Quick text plots over UDP; low activity |
| Serial Studio | GPL-3.0 source; prebuilt binaries need a commercial licence for commercial use ([Serial Studio](https://raw.githubusercontent.com/Serial-Studio/Serial-Studio/master/doc/help/Pro-vs-Free.md)) | Yes | Licence friction |

Neither board has a real-time clock, so **clock sync follows MAVLink's TIMESYNC**. The requester sends its own time, the responder echoes it with its own time added, and the requester estimates the offset from the round-trip time, repeating and filtering to reject outliers ([MAVLink Timesync](https://mavlink.io/en/services/timesync.html)). Micro XRCE-DDS uses the same NTP-style exchange ([Micro XRCE-DDS](https://github.com/eProsima/Micro-XRCE-DDS-docs/blob/master/docs/time_sync.rst)), and Trice advises sending raw counter values and handling wrap-around on the host ([Trice](https://github.com/rokath/trice)). The UNO stamps packets with a 32-bit microsecond counter, which wraps every 71.6 minutes. The computer fits offset and drift from the lowest-round-trip samples every few seconds. Each MCAP message stores host receive time as `log_time`, the converted device time as `publish_time`, and the raw counter as a field. The sync samples go on their own channel, so the fit can be redone offline. At 9600 baud a 10-byte frame takes about 10 ms on the wire, so offsets carry **millisecond-level uncertainty** in stage 2. That is enough for a tank, but the docs should say so.

## Calibration and fault codes share one small UDS-shaped service

D10 and D11 both need a request/response channel. They should share one service with a common design, instead of running two protocols. Four ways to do it were examined.

| Approach | How it works | For | Against |
|---|---|---|---|
| XCP on SxI (serial) | Generic memory read and write, described by an A2L file ([ASAM XCP](https://www.asam.net/standards/detail/mcd-1-xcp/), [Wikipedia](https://en.wikipedia.org/wiki/XCP_(protocol))) | Designed to fit 8-bit MCUs; pyxcp (LGPLv3+) is a master with serial support ([pyxcp](https://github.com/christoph2/pyxcp)) | The SxI framing spec is paid. Raw-address writes bypass validation. It doesn't cover fault codes |
| MAVLink-style parameters | Named scalars, set and echoed back ([MAVLink](https://mavlink.io/en/services/parameter.html)) | Proven on drones; the echo shows what the firmware actually holds | 16-character names cost bytes; no fault codes |
| **UDS-shaped subset (recommended)** | Read and write identifiers, routines, fault-code reads and clears ([udsoncan](https://udsoncan.readthedocs.io/en/latest/udsoncan/services.html)) | One model for both. python-udsoncan can be the tester through a custom connection class. Familiar to an automotive engineer | We write the UNO side ourselves |
| Fully custom messages | Whatever the description defines | Smallest | No existing tester |

The recommended service carries a small subset of UDS service IDs inside our own packets. UDS maps byte arrays to byte arrays, so it runs over a UART with its own framing ([Habr](https://habr.com/en/articles/795385)), and ISO-TP is only needed on short-frame buses ([NI](https://www.ni.com/docs/en-US/bundle/automotive-diagnostic-command-set-toolkit-labview-api-ref/page/uds-unified-diagnostic-services.html)). In the subset, 0x22 reads a parameter and 0x2E writes the RAM working value. 0x31 runs routines to store, restore defaults or reload from EEPROM. 0x19 reads fault codes and 0x14 clears them. The open C stack driftregion/iso14229 (MIT, v0.11.0) **doesn't implement 0x19 and has no fault memory**, shows no AVR example, and says its API isn't stable yet ([iso14229](https://driftregion.github.io/iso14229/)). Its README also strongly discourages AI-written contributions ([GitHub](https://github.com/driftregion/iso14229)). A hand-written UNO subset is the realistic path. The UDS texts themselves are paid ISO standards ([ISO 14229-5 catalog](https://iteh.es/catalog/standards/iso/4e5e685a-c8e3-4a8e-8728-2a23ed20e891/iso-14229-5-2022)), so the details below come from open secondary sources and should be described in our own words, without any claim of conformance.

**Calibration** borrows from drones, then closes the gaps they leave. PX4 holds parameters in RAM until an explicit `param save`, and its minimum and maximum are only "sane value" hints the user can override ([PX4](https://docs.px4.io/main/en/advanced/parameters_and_configurations.html)). ArduPilot keys stored entries by a stable ID behind a magic-and-revision header. It wipes the store on a revision mismatch and writes in a power-safe order, but no CRC covers the stored values ([AP_Param.h](https://raw.githubusercontent.com/ArduPilot/ardupilot/master/libraries/AP_Param/AP_Param.h), [AP_Param.cpp](https://raw.githubusercontent.com/ArduPilot/ardupilot/master/libraries/AP_Param/AP_Param.cpp)). MAVLink requires the vehicle to echo the value after every set, even when the write fails ([MAVLink](https://mavlink.io/en/services/parameter.html)). The design here keeps the RAM working set and the explicit store, keys parameters by stable numeric IDs, and **enforces** the description's limits. After each write it replies with the value it actually holds. Stored sets go into two EEPROM slots, A and B. Each slot holds magic, layout version, schema hash, sequence counter, length, payload and CRC-16. At boot the UNO takes the valid slot with the highest sequence number, and falls back to compiled-in defaults if neither is valid, which is what D10 requires. A store writes the other slot, so a power cut mid-write leaves the old set intact. EEPROM writes take about **3.3 ms per byte**, and the cells last at least 100,000 cycles ([datasheet mirror](https://cn.elcodis.com/parts/1289539/ATMEGA328P-AU_p23.html), [Microchip](https://onlinedocs.microchip.com/oxy/GUID-74F8229E-4C43-4FA0-BE7D-1AA303C6F8A4-en-US-6/GUID-EE5E33C8-EF0F-4A12-BD91-EC7DB0A1725C.html)). Storing a 64-byte set therefore takes about 0.21 s. That would break T2's 5 ms loop limit if done in one go, so the store runs one byte per EEPROM-ready interrupt, or only while the motors are stopped. On the ESP32-S3, NVS is already a wear-levelled, power-loss-tolerant log, but nothing is durable until `nvs_commit()` ([ESP-IDF NVS](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/storage/nvs_flash.html)).

**Fault codes** use the ISO 14229 model at a small scale. Each one has a 3-byte code and a status byte with eight flags. The flags cover failed now, failed this operation cycle, pending, confirmed, not completed since clear, failed since clear, not completed this cycle, and warning requested. Each code also has a signed 8-bit debounce counter and an ageing counter, with a usual threshold of 40 operation cycles ([py-uds](https://uds.readthedocs.io/en/stable/pages/knowledge_base/dtc.html)). Robotics diagnostics are mostly live status, with no fault memory. ROS 2 `/diagnostics` reports OK, WARN, ERROR or STALE, and MAVLink SYS_STATUS reports present, enabled and healthy bitmaps ([ROS diagnostics](https://github.com/ros/diagnostics), [MAVLink](https://mavlink.io/en/messages/common.html#SYS_STATUS)). The ROS community is itself discussing what's missing ([Discourse](https://discourse.openrobotics.org/t/whats-missing-from-ros-2-diagnostics-and-what-we-built/52489)). The robot needs both. Its monitors feed a persistent fault memory, and the same flags drive a live health bitmap in telemetry and a "ready to drive" check like ArduPilot's pre-arm checks ([ArduPilot](https://ardupilot.org/copter/docs/common-prearm-safety-checks.html)).

Sizing is design arithmetic, because no published reference design exists (**estimate**). Sixteen fault definitions live in flash at about 8 bytes each. RAM holds 3 bytes per fault code, 48 bytes in all. Each stored EEPROM entry is about 12 bytes: an index, status, occurrence and ageing counters, plus an 8-byte first-occurrence snapshot of battery mV, uptime, mode, both motor PWMs and one fault-specific value. Sixteen entries use about 200 bytes, and two calibration slots of 128 bytes about 280 more, leaving about half the 1 KB EEPROM free. EEPROM is written only when a code is confirmed or cleared, or at the end of an operation cycle, so fewer than ten writes per drive. The unexpected-reset monitor would read the reset-cause register at boot, but whether Optiboot 4.4 ([UNO backup](../notebook/2026-11-04-backing-up-the-uno.md)) preserves that register, or RAM marked `.noinit`, is **[unverified]**. Until that is tested, the monitor may only be able to log a boot count. In stage 3 the ESP32 keeps its own fault codes in NVS and acts as the gateway that answers fault-code reads for both boards, the way a vehicle gateway does.

## The UNO's share fits T8 on paper

The table is an **estimate**, built from the component sizes above and typical hand-written C++ sizes. Nothing has been compiled. T8 allows at most 80% of the 32,256 bytes the build reports (about **25.8 KB**), and at least 512 bytes of RAM left free, which leaves 1,536 bytes to use ([first look](../notebook/2026-11-03-first-look-at-stock-firmware.md), [requirements](../requirements.md)).

| Part | Flash (estimate) | RAM (estimate) |
|---|---|---|
| UART driver with 32-byte RX and TX rings | 0.4–0.8 KB | 64–128 B |
| Envelope codec (COBS, plus Base64 for stage 2) | 0.2–0.6 KB | 0 (works in place) |
| CRC-16, bitwise, no table | 0.05–0.15 KB | 0 |
| Packet buffers, RX and TX, 40 B each | – | 80 B |
| Generated pack and unpack, about 20 message types | 1–2.5 KB | stack only |
| Session: HELLO, 300 ms watchdog, sequence and acks, time sync | 0.3–0.7 KB | 16–24 B |
| Log token queue, 8 entries of 8 B | 0.2–0.5 KB | 64 B |
| Calibration: working set, A/B store, CRC, limits | 0.8–1.5 KB | 64–128 B |
| Fault codes: 16 definitions, debounce, snapshots, read and clear | 1–2 KB | 48–80 B |
| Service dispatcher | 0.4–0.8 KB | 8–16 B |
| **Total** | **about 4.5–9.5 KB (17–37% of the T8 allowance)** | **about 350–520 B (23–34% of the T8 allowance)** |

Stack peaks during service handling add perhaps 50 to 100 bytes more. For comparison, the stock firmware used **1,153 bytes of static RAM and 98% of flash**, about 15 KB of it in libraries such as ArduinoJson, String and float routines ([first look](../notebook/2026-11-03-first-look-at-stock-firmware.md)), none of which this design needs. The biggest levers are the serial ring sizes and the calibration working-set size. The first firmware build should report `avr-size` per module, so these guesses get replaced by measurements quickly.

## Decisions for the maintainer

1. **Description source:** our own YAML schema with a Python generator (recommended), DBC as the source with cantools, or MAVLink XML with a custom dialect.
2. **Industry exports:** which of DBC, A2L and ODX to build, and when. The suggestion is DBC first, because it is cheap and well supported by open tools, with A2L and ODX deferred until a real use appears.
3. **Stage 2 link paths:** support both the stock bridge (Base64 in braces at 9600) and USB (COBS at a higher baud) in one build, or use USB only for development and the bridge only to prove S3 and T7 over Wi-Fi.
4. **Stage 3 UART baud:** 250k (recommended) or 500k, chosen after the GPIO3 measurement and the ESP32 divider check.
5. **Bridge style in stage 3:** frame-aware forwarding (recommended), fully terminating, or transparent.
6. **Wi-Fi transports in stage 3:** UDP for the computer tool plus WebSocket for the browser (recommended), or WebSocket for both to keep one code path.
7. **Packet header:** whether to include the 1-byte route field from the start, and the payload cap (32 bytes suggested).
8. **Logging:** log events declared in the description (recommended), or a Trice spike first.
9. **Calibration and diagnostics service:** a UDS-shaped subset with python-udsoncan as the tester (recommended), MAVLink-style parameters, or XCP on serial.
10. **Calibration storage:** per-parameter stable IDs, so newer firmware can load the parameters it knows and default the rest, or a whole-struct blob that is rejected on any layout change. Also when a store is allowed: any time with byte-per-interrupt writes, or only with the motors stopped.
11. **Write protection:** whether writes and fault-code clears need a session or password step. This links to S11, because the stock access point is open.
12. **Fault-code policy:** the first list of codes, the numbering range, what counts as an operation cycle (power-on to power-off is suggested), the confirm and ageing thresholds (40 cycles is the common default), and one copy with per-entry CRCs or A/B copies.
13. **Recording:** MCAP through the Foxglove SDK (recommended); JSON with JSON Schema or protobuf for decoded channels; and whether to always record raw link packets alongside them.
14. **Supported viewer:** Lichtblick (recommended, once it is tested with the SDK server), PlotJuggler, Rerun, or Foxglove with an account. Also whether the computer tool needs its own plots.
15. **Cross-session analysis:** a Parquet and DuckDB pipeline in stage 2, or later when there are enough recordings to matter.
16. **Compatibility identity for D15:** whether the 4-byte description hash alone defines "made to work together", or a release manifest that also lists firmware and calibration versions. Also confirm that the flashing tool, not the bootloader, enforces it on the UNO.

## Conclusion

The project's most useful asset turns out to be a file, not any protocol: one description from which the UNO's packers, the computer's decoders, the recording schemas, the log dictionary, the calibration limits and the fault table all follow. That file is what makes D13's "add a signal, see it in the tool" possible. Its hash is the cheapest way to meet D15, and attached to each recording it keeps old sessions decodable after the format changes. The automotive formats are still worth knowing as export targets, but the open-source drone ecosystem has shown that a small generator and a CRC_EXTRA-style hash give most of their value at a fraction of the cost.

The stage boundary matters more than any format choice. Stage 2 is held to 9600 baud and braces by firmware we don't control, so the design has to keep its envelope swappable and its safety local to the UNO from the start. If the 300 ms timer, idempotent stops and small frames are right at 9600 baud through a bridge built for a toy app, the faster stage 3 link only makes the margins bigger.
