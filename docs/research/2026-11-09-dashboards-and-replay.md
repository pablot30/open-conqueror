# Borrow the race replay's shape, not its code

> **Published on 2026-11-16.** Written on 9 November 2026 and kept out of the repo until the maintainer decided to publish its possibly novel ideas openly. Unchanged since then apart from links into the repo, the final section, and one sentence about a viewer's licence holder, which now points to the [novelties](../novelties/README.md). Read it as background: where a [decision](../decisions/README.md) says otherwise, the decision wins.

Research date: 9 November 2026. Stars, release numbers and dates come from the GitHub REST API on that day and will drift. **[unverified]** marks claims that weren't confirmed against a primary source. Design ideas that aren't facts are labelled **inference**. Nothing here was built or tried on the robot.

f1-race-replay's code isn't safe to reuse, but its design is worth copying, and most of the evaluation tool already exists as open software. The project puts every signal on **one 25 FPS timeline** and moves a single cursor through it. Every other window **subscribes to a local socket** and follows that cursor. The same split suits open-conqueror: one small Python "hub" owns the robot link, records MCAP files and publishes one stream, and every view subscribes, whether the source is the live robot or a recording. Three open viewers already cover much of D7 to D9 with no UI code from us. Lichtblick (MPL-2.0, browser and desktop) is the closest to a ready-made panels-and-timeline tool. PlotJuggler (MPL-2.0) is the best at comparing runs, and Rerun (Apache-2.0) is the easiest to feed from Python. What no viewer provides is the robot-specific part: driving, a calibration editor that writes values back, a fault-code panel with read and clear, a session search across recordings, and a clearly labelled estimate of the robot's path. Those are ours to build. The drive page should be written once as a small web bundle, served by the hub on the computer in stage 2 and from the ESP32-S3's flash in stage 3. The control-page lessons come from Espressif's own camera example and from ESPHome. Keep video and control on separate connections, show how old the video is and how long commands take, embed every asset so the page works with no internet, and stop the robot when the link goes quiet. Licences sort the field cleanly. Apache-2.0, MIT and BSD projects can be reused with notices, and MPL-2.0 viewers are fine to run as external tools. GPL, AGPL and EUPL projects are inspiration only, and so is f1-race-replay, which claims MIT in its README but has no licence file.

## f1-race-replay is a 25 FPS timeline with windows listening on a socket

f1-race-replay is a Python desktop app that replays Formula 1 sessions. It shows every car moving on a drawn track, with a leaderboard, weather, DRS zones and standings. It is popular and young: **6,966 stars and 910 forks, created on 21 November 2025, last pushed on 24 October 2026, with no releases or tags**, so users run it from `main` ([GitHub API](https://api.github.com/repos/IAmTomShaw/f1-race-replay), [releases](https://api.github.com/repos/IAmTomShaw/f1-race-replay/releases)). It gets its data from FastF1. FastF1's own docs now say it **"requires an F1TV Access subscription (or higher plan) for most of its features"**, a change f1-race-replay's README doesn't mention ([FastF1 docs](https://docs.fastf1.dev/)). The replay window uses Python Arcade on OpenGL 3.3, and the side windows use PySide6 (Qt) ([race_replay.py](https://github.com/IAmTomShaw/f1-race-replay/blob/main/src/interfaces/race_replay.py), [telemetry.md](https://github.com/IAmTomShaw/f1-race-replay/blob/main/telemetry.md)).

The architecture is simple, and that's why it's worth studying. At load time, each car's telemetry is processed in parallel. A global timeline is built at **25 FPS (one tick every 40 ms)**, and every signal (position, distance, lap, tyre, speed, gear, DRS, throttle, brake) is resampled onto it with `np.interp`. Track status and weather are aligned to the same ticks, giving one dictionary per tick for the whole race ([f1_data.py](https://github.com/IAmTomShaw/f1-race-replay/blob/main/src/f1_data.py)). Playback is a float `frame_index`. Each screen update adds `delta_time × FPS × playback_speed`, the drawn frame is `frames[int(frame_index)]`, and speed steps through a fixed list **from 0.1x to 256x** ([race_replay.py](https://github.com/IAmTomShaw/f1-race-replay/blob/main/src/interfaces/race_replay.py)). The keyboard controls are a good baseline to copy: space pauses, the left and right arrows rewind and fast-forward, the up and down arrows change speed, 1 to 4 pick preset speeds and R restarts ([README](https://github.com/IAmTomShaw/f1-race-replay/blob/main/README.md)). A progress bar carries **event markers** taken from the race, and the track changes colour with the track status ([race_replay.py](https://github.com/IAmTomShaw/f1-race-replay/blob/main/src/interfaces/race_replay.py)).

The most transferable idea is the **telemetry bus**. The replay runs a TCP server on `localhost:9999` and sends each frame as one line of JSON to every connected client. The payload carries the frame, its index, the total frame count, whether playback is paused and its speed. It also resends the full lap history every time, so a newly opened window catches up at once ([stream.py](https://github.com/IAmTomShaw/f1-race-replay/blob/main/src/services/stream.py), [telemetry.md](https://github.com/IAmTomShaw/f1-race-replay/blob/main/telemetry.md)). Each "insight" window (lap times, tyre strategy, sector times, a raw telemetry viewer) runs as its own process. It subclasses a `PitWallWindow` base class and implements just two methods, `setup_ui()` and `on_telemetry_data(data)`. The base class handles the connection, the status bar and cleanup ([run_session.py](https://github.com/IAmTomShaw/f1-race-replay/blob/main/src/run_session.py), [README](https://github.com/IAmTomShaw/f1-race-replay/blob/main/README.md)). The replay is the clock, and the windows only listen. Two smaller habits are also worth copying. The docs say that **`null` means "unknown", not zero** ([telemetry.md](https://github.com/IAmTomShaw/f1-race-replay/blob/main/telemetry.md)). And because the data has no position for the safety car, the app **draws a simulated one about 500 m ahead of the leader and says it is simulated** ([README](https://github.com/IAmTomShaw/f1-race-replay/blob/main/README.md)). That second habit is exactly how a robot with no encoders should show its estimated path.

The project also shows what not to do. It interpolates every signal linearly, gear and DRS included ([f1_data.py](https://github.com/IAmTomShaw/f1-race-replay/blob/main/src/f1_data.py)). For a robot that would blur mode changes and fault states, which should hold their last value instead (**inference**). It caches computed frames as pickle files ([f1_data.py](https://github.com/IAmTomShaw/f1-race-replay/blob/main/src/f1_data.py)), and its dependencies aren't pinned ([requirements.txt](https://github.com/IAmTomShaw/f1-race-replay/blob/main/requirements.txt)). CI runs on Linux only, for Python 3.10 to 3.12 ([tests.yml](https://github.com/IAmTomShaw/f1-race-replay/blob/main/.github/workflows/tests.yml)). Its own roadmap admits that drawing some of the UI "is starting to cause noticeable lag during race replays" and asks for "de-cluttering" ([roadmap.md](https://github.com/IAmTomShaw/f1-race-replay/blob/main/roadmap.md)). The licence settles the reuse question. The README says MIT, but the repository has **no LICENSE file and GitHub detects no licence** ([README](https://github.com/IAmTomShaw/f1-race-replay/blob/main/README.md), [GitHub API](https://api.github.com/repos/IAmTomShaw/f1-race-replay)). Until a licence file appears, the code should be treated as all rights reserved: **inspiration only**.

## Race tools and drone ground stations agree on one clock, coded faults and described parameters

Across F1 replays, sim-racing tools and robotics plotters, the same feature set keeps returning (**inference** from the tools below). There is one master timeline that you can scrub and speed up. Several views, such as plots, a map and tables, follow that timeline. A 2D track map shows a marker, often coloured by a signal. Two laps or runs can be overlaid with a difference trace. Events are marked on the timeline, and sessions are recorded locally and replayed. The open sim-racing tools show the pattern clearly. RaceIQ (**AGPL-3.0**) records laps to a local database, compares laps side by side with time deltas and draws a live track outline ([GitHub API](https://api.github.com/repos/SpeedHQ/RaceIQ), [repo](https://github.com/SpeedHQ/RaceIQ)). TelemetryIQ (**MIT**) has a live WebSocket display, per-lap SQLite recording, a driving line coloured by speed, and a delta against a reference lap ([GitHub API](https://api.github.com/repos/a1exus/TelemetryIQ)). Putting data on video is a niche of its own. gopro-dashboard-overlay (**GPL-3.0**, 589 stars) burns gauges and maps from logged GPS data into the video file ([GitHub API](https://api.github.com/repos/time4tea/gopro-dashboard-overlay)).

The motorsport data sources themselves are poor models for reuse. OpenF1 publishes car telemetry at **3.7 Hz** and positions every 4 s, with live data only on a paid tier ([openf1.org](https://openf1.org/)). Its repository licence is **CC BY-NC-SA 4.0**, which rules it out for an Apache-2.0 project ([licence](https://api.github.com/repos/br-g/openf1/license)). That rate puts the robot in perspective. T7 asks for sensor data at **10 Hz or more** ([requirements](../requirements.md)), which is more detail than the public F1 feeds give fans. At 9600 baud through the stock bridge, a 24-byte telemetry payload grows to about 42 bytes once framed and Base64-encoded. At 10 Hz that uses roughly 44% of the UNO's roughly 960 bytes a second of transmit capacity (**estimate**, design arithmetic from the stock bridge limits in [camera board](../hardware/camera-board.md#working-with-the-stock-bridge)). Stage 2's live view is therefore limited by the link, not the UI. A 25 FPS display would just redraw the same samples.

Drone ground stations solved the evaluation tool's harder parts years ago, and their patterns transfer without their protocol. QGroundControl (**Apache-2.0**, Qt, Windows, macOS, Linux, Android and iOS from one codebase) has a parameter screen that is the best model for D10. Parameters are grouped. Search matches **descriptions as well as names**. Clicking a row opens an edit dialog with more detail, and a toolbar flag says **"reboot required"** until the vehicle restarts. A Tools menu offers reset to defaults and save to or load from a file ([QGC README](https://github.com/mavlink/qgroundcontrol), [QGC docs: Parameters](https://docs.qgroundcontrol.com/master/en/qgc-user-guide/setup_view/parameters.html)). The same docs page says nothing about showing minimum, maximum, units or defaults, or about a "modified only" filter, so whether QGC shows them is **[unverified]**. QGC also has a built-in MAVLink Inspector, log download and video recording ([QGC README](https://github.com/mavlink/qgroundcontrol)). ArduPilot's logs show what D11 needs on a timeline. Its ERR messages pair a subsystem with an error code, and an explicit **"cleared" code** marks recovery, so the log records both when a fault started and when it ended. EV messages record events such as arming. PARM rows write the **parameter set into every log**, so a replay shows the calibration it ran with ([ArduPilot docs](https://ardupilot.org/planner/docs/common-downloading-and-analyzing-data-logs-in-mission-planner.html)). Mission Planner, the app those docs describe, is **GPL-3.0** C# and Windows-first ([GitHub](https://github.com/ArduPilot/MissionPlanner)). MAVProxy is a **GPL-3.0** Python command-line station ([GitHub](https://github.com/ArduPilot/MAVProxy)). Both are inspiration only. MAVProxy's role, one link in and many consumers out, is the shape of the hub recommended below.

## Three open viewers cover much of D9 before we write any UI

If the hub records MCAP, three maintained open viewers become available on day one. **Lichtblick** describes itself as a "visualization and diagnosis tool for robotics, available in your browser or as a desktop app on Linux, Windows, and macOS". It is a TypeScript fork of the last open Foxglove Studio, licensed **MPL-2.0**, at v1.30.0 (22 October 2026), and it has a hosted browser build ([GitHub](https://github.com/Lichtblick-Suite/lichtblick), [package.json](https://github.com/Lichtblick-Suite/lichtblick/blob/main/package.json)). One directory calls it "open core", which the repository doesn't support, so that claim is **[unverified]** ([awesome.ecosyste.ms](https://awesome.ecosyste.ms/projects/github.com%2Flichtblick-suite%2Flichtblick)). **PlotJuggler 4** (**MPL-2.0**, 4.1.0 on 5 November 2026) is the strongest signal plotter. You drag signals into time and XY plots, load several recordings, "align their timelines, and overlay signals", derive new series in Lua or Python, and save layouts. It reads CSV, MCAP, Parquet and video, and takes live data over MQTT, ZeroMQ, UDP and WebSocket in JSON, CBOR or Protobuf ([PlotJuggler](https://github.com/PlotJuggler/PlotJuggler)). **Rerun** (Apache-2.0 per GitHub, 0.42.0 on 4 November 2026, still before 1.0) has a Python SDK with named timelines. Its viewer "renders everything in sync" for live data and for saved `.rrd` files, natively or in a browser, and it reads MCAP ([Rerun](https://github.com/rerun-io/rerun), [What is Rerun](https://rerun.io/docs/overview/what-is-rerun)). Rerun's `.rrd` files only reliably open in adjacent versions ([Rerun](https://rerun.io/docs/reference/sdk/operating-modes)), so `.rrd` should be a view-time format and never the archive.

Foxglove itself closed its open edition in March 2024. Its MCAP format stayed open ([Open Robotics Discourse](https://discourse.openrobotics.org/t/foxglove-2-0-integrated-ui-new-pricing-and-open-source-changes/36583), [archived repo](https://github.com/foxglove/studio)). Its **MIT** SDK still matters here: one Python script can open an MCAP file and a local WebSocket server at the same time, and every `log()` call goes to both ([Foxglove SDK](https://docs.foxglove.dev/docs/sdk/example)). That is the hub's recording and live-serving core, ready-made.

## Phone pages that work keep video and control on separate connections

Espressif's own camera example sets the standard pattern for a page served from an ESP32. It runs **two HTTP servers**. Control and status live on the main port. A second server on the next port up serves only `/stream`, a long-running `multipart/x-mixed-replace` MJPEG response, so video never blocks a control request. Each JPEG part carries an **`X-Timestamp`** header ([app_httpd.cpp](https://github.com/espressif/arduino-esp32/blob/master/libraries/ESP32/examples/Camera/CameraWebServer/app_httpd.cpp)). The stock camera firmware has the same layout: `/control`, `/status` and `/capture` on port 80, and `/stream` on port 81 ([camera board](../hardware/camera-board.md)). Whether its stream also carries `X-Timestamp` is **[unverified]**. The example's handlers all send `Access-Control-Allow-Origin: *` with no authentication ([app_httpd.cpp](https://github.com/espressif/arduino-esp32/blob/master/libraries/ESP32/examples/Camera/CameraWebServer/app_httpd.cpp)), and the stock access point has no password ([camera board](../hardware/camera-board.md)). Our page must do better, as S11 already requires.

Hobby robot cars add a WebSocket for joystick commands, and some also send camera frames over a WebSocket, for example at up to 24 Hz ([Hackaday.io: WALL-E](https://hackaday.io/project/165989-wall-e), [DFRobot wiki](https://wiki.dfrobot.com/dfr0994/docs/22833)). Good latency data is scarce. One paper on an ESP32-CAM car reports **under 200 ms** command latency and calls MJPEG streaming latency a major challenge. That comes from a search summary, and its full figures weren't read **[unverified]** ([AIRCC CSIT](https://aircconline.com/csit/papers/vol16/csit160511.pdf)). One Hackaday comment reports about 1 s of lag on a slow tracked toy, which is an anecdote, not a measurement ([Hackaday](https://hackaday.com/2025/02/06/rc-cars-with-first-person-video-all-with-an-esp32)). The robot's own numbers will have to be measured.

ESPHome's built-in page is the closest model for a status page hosted on an ESP32. It is one JavaScript bundle of about 9 KB compressed, built from web components, with light and dark themes and a **30-second heartbeat** that shows whether the node is still connected ([esphome-webserver](https://github.com/esphome/esphome-webserver)). Its configuration shows what matters in practice ([ESPHome web_server](https://esphome.io/components/web_server/)). The `local: true` option embeds the CSS and JavaScript so the page works **without internet access**, which is the robot's situation on its own access point. Live state and logs arrive over Server-Sent Events. Version 3 groups and orders entries, shows numbers as sliders, and opens **a history graph when you tap a sensor**. The docs also warn that **each connected client uses heap memory**, that cross-origin requests are now restricted by default, and that web firmware updates without `auth:` let "anyone who can reach the device" upload firmware. Vizanti, a phone-first robot map served from the robot, adds two practical lessons. It saves client settings in localStorage, and Android phones on a hotspot with no internet should turn off mobile data, or traffic may go to the wrong gateway ([Vizanti](https://github.com/MoffKalast/vizanti)). WLED's named presets, recalled with one tap, are a good model for mode buttons ([WLED](https://github.com/wled/WLED)).

Put together for F12, the page is a single column on a phone (**inference**). Video goes at the top, shown as MJPEG in an `<img>` from its own server. Below it come a thumb pad for eight-direction driving with a speed slider, a pan and tilt pad, mode buttons styled as presets, LED brightness and a large stop button. A status strip shows battery, link state, active fault count, video age (from the frame timestamp) and command round-trip time. Drive commands are small, sequence-numbered messages sent on a WebSocket at a fixed 10 to 20 Hz. Releasing the pad sends stop. If the page is hidden or the socket goes quiet, the UNO's own 300 ms timer stops the tank, as S3 requires ([requirements](../requirements.md)). Pan and tilt are servos on the UNO's D10 and D11 ([pin map](../hardware/pin-map.md)), so they travel over the same link as driving. They aren't a camera-board feature.

## One hub on the computer feeds every view, live or replayed

The recommended architecture copies f1-race-replay's clock-and-subscribers shape, with an open file format and a browser-friendly bus (**inference**, built on the facts above). One Python process, the **hub**, runs in the project's uv virtual environment. It owns the robot link: the stock bridge on TCP port 100 or USB in stage 2, and UDP in stage 3. It decodes packets with the decoders generated from the protocol description and stamps both the robot's own clock and the host's receive time. It writes everything to MCAP, where each message has a `log_time` and a `publish_time` ([MCAP spec](https://mcap.dev/spec)). It publishes the same stream on a local WebSocket. The Foxglove SDK (MIT) already does both writing and publishing in one call ([Foxglove SDK](https://docs.foxglove.dev/docs/sdk/example)). For replay, the hub reads an MCAP file and becomes the clock, as f1-race-replay's replay window does. Every view stays the same, because it can't tell a live robot from a recording.

```
 Robot link (TCP 100 / USB, later UDP)        Recording (.mcap)
              \                               /
               +--> HUB (Python, uv venv) <--+
                    decode, timestamp, record, play back, single video pull
                    |                 |                       |
     Foxglove-protocol WebSocket   our own WebSocket       MCAP files
                    |                 |                       |
              Lichtblick       our web pages            PlotJuggler, Rerun,
          (panels, plots)   (drive, calibration,       Parquet + DuckDB
                            faults, sessions, path)    (across sessions)
```

Recordings store raw samples, never a resampled grid. Views resample only for display. Continuous signals are interpolated, and modes, fault states and other discrete values hold their last value (**inference**, avoiding f1-race-replay's interpolated gear). Each recording carries what D14 asks for: a session metadata record, the parameter set in force (as ArduPilot's PARM rows do), and fault set and clear events on their own channel, so Lichtblick shows them too. MCAP supports metadata records and attachments ([MCAP spec](https://mcap.dev/spec)). Video comes from two places. In stage 2 the stock firmware already streams MJPEG on port 81, which a browser can show directly ([camera board](../hardware/camera-board.md#working-with-the-stock-bridge)). The hub should pull that stream **once**, store the frames on their own MCAP channel stamped with receive time, and pass them on to the page. Pulling it twice would cost the ESP32 heap for a second client, as ESPHome warns ([ESPHome web_server](https://esphome.io/components/web_server/)). Phone video taken from outside the robot needs an offset. The simplest method is a sync event the hub logs and the camera can see, such as an LED flash, followed by one stored offset per session (**inference**). The robot has a WS2812 LED but no buzzer ([hardware](../hardware/README.md)), so the sync has to be visual.

The estimated path needs the most honesty. The tracks have **no encoders**, and the only motion sensor is an MPU6050 ([hardware](../hardware/README.md), [motor driver](../hardware/motor-driver.md)). A path can therefore integrate the gyro's yaw for heading and take speed from a commanded-PWM model. Track slip and battery voltage will make that speed wrong, so the map must say **"estimated"** and show its error growing, the way f1-race-replay labels its simulated safety car (**inference**). For layout, f1-race-replay's method works unchanged. It rotates, scales and fits the path to the window once and recomputes only on resize ([race_replay.py](https://github.com/IAmTomShaw/f1-race-replay/blob/main/src/interfaces/race_replay.py)). The path can also be coloured by a signal, as TelemetryIQ colours its driving line by speed ([GitHub API](https://api.github.com/repos/a1exus/TelemetryIQ)). Run comparison should align two sessions on an event, such as the start of a mode, and overlay them with a difference trace, as PlotJuggler and the sim tools do ([PlotJuggler](https://github.com/PlotJuggler/PlotJuggler)). The roadmap chose not to record stock behaviour as a reference ([roadmap](../roadmap.md)), and stock firmware won't speak our protocol anyway. Comparisons are therefore mainly our run against our run, for example before and after a calibration change.

### A phased path: reuse first, build only what viewers can't do

| Phase | When | What we build | What we reuse | Requirements served |
|---|---|---|---|---|
| 0. Record and view | Start of stage 2 | Hub: link, decode, MCAP with metadata, live WebSocket; Lichtblick layouts saved as files in the repo | Foxglove SDK, mcap (both MIT); Lichtblick, PlotJuggler, Rerun as external viewers | D7, D8, D9; most of D14's context |
| 1. Drive from the computer | Stage 2 | Small web page served by the hub on localhost: eight-direction driving, modes, pan and tilt, LED, live readings, stop, record button, port 81 video relayed through the hub | Espressif and ESPHome patterns | F11, S1, S3 checks, T7 timing |
| 2. Write back | Stage 2 | Calibration editor built from the parameter metadata; fault panel with read, clear and snapshot; list and search of sessions | QGC and ArduPilot patterns; Parquet and DuckDB for search across sessions | D10, D11, D14 |
| 3. Replay views viewers lack | Late stage 2, only if Lichtblick falls short | Timeline with event markers, estimated path map, video offset sync, run overlay | f1-race-replay controls, PlotJuggler overlays | D9, D14 |
| 4. Phone page on the robot | Stage 3 | The phase 1 page, embedded gzipped in ESP32-S3 flash, with WebSocket control, password and origin checks | ESPHome front-end approach (MIT) | F12, F17, S11 |

Phases 1 and 4 are the same page (**inference**). If it is written as plain TypeScript web components with a small bundle, as ESPHome's front end is ([esphome-webserver](https://github.com/esphome/esphome-webserver)), the hub can serve it in stage 2, bridging its WebSocket to the bridge's TCP port. That fits decision 0004, which says browsers can't reach port 100 directly ([0004](../decisions/0004-own-protocol-and-control-page.md)). In stage 3 the camera board serves the same bundle from flash. NiceGUI would get phase 1 running sooner in pure Python ([NiceGUI](https://github.com/zauberzeug/nicegui)), but a NiceGUI page can't move onto the ESP32, so the drive page would be written twice. NiceGUI is still reasonable for the computer-only views in phase 2. A TypeScript build needs Node.js on the machines that build the bundle, which the project's keep-computers-clean rule makes a deliberate choice (decision 4 below). A Qt app like f1-race-replay's, or Dear PyGui, would need a separate phone UI ([Dear PyGui](https://github.com/hoffstadt/DearPyGui)). A desktop wrapper adds a window but no capability, and Tauri's next major version is still alpha ([Tauri](https://github.com/tauri-apps/tauri)). A browser tab is enough for now.

## Decisions for the maintainer

1. **First viewer:** Lichtblick as the supported viewer (recommended, once the live-server test passes), PlotJuggler, Rerun, or all three with no official one.
2. **Hub:** one Python process in the uv venv that owns the link, records MCAP through the Foxglove SDK and serves every view (recommended), or a separate recorder and UI.
3. **Our pages' technology:** plain TypeScript web components with a small bundle that can later sit in ESP32 flash (recommended), or NiceGUI in pure Python for a faster start, with the stage 3 page written separately.
4. **Node.js:** if TypeScript is chosen, whether Node.js is installed on development machines (listed in `docs/tools.md`), or the bundle is only built in CI and committed or downloaded.
5. **One drive page, hosted twice:** serve the F11 page from the hub in stage 2 and the same bundle from the camera board in stage 3 (recommended), or build the stage 3 page from scratch.
6. **Hub exposure in stage 2:** localhost only (recommended, matching 0004's "no phone control in stage 2" and S11), or reachable on the robot's network so a phone can drive in stage 2.
7. **Where calibration and faults live:** in our own page, because they write to the robot (recommended), or as Lichtblick panels if its extension API allows writing.
8. **Onboard video in stage 2:** record the port 81 stream into MCAP through a single hub pull, and at what frame rate and resolution cap, or leave video out of recordings until stage 3.
9. **Outside video:** a manual offset with an LED-flash sync event (recommended first), or automatic detection later.
10. **Estimated path:** build it in phase 3 from gyro heading and a PWM speed model, labelled as estimated, or leave it out until better sensing exists.
11. **Run comparison:** which events align runs (mode start, first motor command, a stop), and confirm that comparisons are our runs against our runs.
12. **Code reuse policy:** allow copying from Apache-2.0, MIT and BSD projects (ESPHome's front end, Espressif's example, Vizanti, Open MCT) with notices, and keep MPL-2.0 viewers as external tools only (recommended).
13. **Desktop packaging:** none for now, a browser tab (recommended), or Tauri once its next version is stable.

## Conclusion

The research changes where the effort goes. Plots, panels and replay are now commodities with open, maintained viewers. The parts that are truly ours are the ones that touch the robot: the link, the recorder's context, and the write paths for calibration and fault codes. Each of these follows from the protocol description the earlier research recommended, and a viewer can't supply any of them. f1-race-replay is useful for a different reason than expected. Its code is off-limits and its structure is straining, but its two core moves, one clock with listening windows and an honest "simulated" label, are exactly what a robot with a slow link and no encoders needs.

The stage boundary helps here as well. A drive page written once, served by the computer while the stock bridge stands and by the robot once it doesn't, turns decision 0004's two-stage plan into one piece of UI work. The link, not the UI, sets the limit in stage 2. At 9600 baud the live view gets about 10 samples a second, so stage 2 rewards spending effort on what is recorded and how it is labelled more than on how smoothly it is drawn.

## Possibly novel ideas

No prior-art search was done for these, and both are close to established practice. They're published as novelties [N4](../novelties/N4-led-colour-timecode.md) and [N5](../novelties/N5-fault-memory-on-the-replay-timeline.md).

1. **A colour-coded LED timecode for video sync.** The robot's WS2812 LED would flash a short colour sequence encoding the hub's clock at intervals. The hub would find it in phone video to work out both the offset and the clock drift automatically, instead of using one manual offset. Visual timecodes and sync flashes are long-established in film and motion capture, so this is probably not new. Using the robot's single status LED and the protocol's time sync together may still be worth a check.
2. **Evaluation UI generated from the single description file.** The same YAML that defines the protocol would also generate the calibration editor's fields and limits, the fault panel's codes and snapshot layout, the timeline's event-marker types and the viewer layouts. Fault-status transitions in the style of ISO 14229 would be drawn on the replay timeline next to the snapshot taken at that moment. Metadata-driven parameter screens (QGC) and telemetry dictionaries are established, but this combination, joining automotive-style fault memory to a robotics replay timeline through one description, wasn't found in the sources read.
