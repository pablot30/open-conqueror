# R5: Embedded toolchain and build

**Background research from 9 November 2026, written before [decision 0006](../decisions/0006-walking-skeleton-first.md) cut stage 2 back to a walking skeleton.** Its recommendations are input, not decisions. Where a decision or the [architecture](../architecture.md) says otherwise, they win.

**In one line:** Build each board natively around one portable core.

Research date: 9 November 2026. Sources are cited inline. **[unverified]** marks a claim that no primary source confirmed during this research, usually because it comes from general knowledge. **Measured** means it was run on the maintainer's Mac. Repo links point at the open-conqueror checkout next to this folder.

No single build tool fits this robot, so the project should use a **hybrid**. The UNO builds with **arduino-cli 1.5.1 and a pinned `sketch.yaml` profile** on the `arduino:avr` 1.8.8 core, which is already installed. The ESP32-S3 builds with **ESP-IDF and `idf.py`**. Host unit tests build with **CMake presets, Clang, GoogleTest and llvm-cov**. All three compile the same board-independent "portable core" folder, and a `just` file calls small Python scripts run through uv, so every command is the same on macOS, Linux and Windows. The single-tool alternatives each fail one hard requirement. arduino-cli has no host tests. PlatformIO has no Clang MC/DC support, depends on one main maintainer, and its ESP32 support lagged years behind until October 2026. A pure-CMake build would mean writing our own AVR toolchain, because every Arduino-CMake project has gone dormant. The common C++ profile is **C++17 with no exceptions, no RTTI and no heap**, and **ETL 20.49.0** replaces the standard library, which the AVR compiler doesn't ship at all. CI compiles the portable core with three compilers to catch drift. Debugging is lopsided. The ESP32-S3 gets **full breakpoint debugging over its existing USB cable** at no hardware cost. Breakpoints on the UNO need debugWIRE, and debugWIRE needs the **auto-reset capacitor disconnected, which is a hardware change** that decision 0001 defers. That collides with requirement D12 in stage 2, so the maintainer has to choose a way through. Several key steps are untested, so a short proof-of-concept spike should come before any firmware.

## A hybrid beats any single build tool for this robot

The project needs four things from its build: firmware for an ATmega328P, firmware for an ESP32-S3, host tests with 100% line, branch and MC/DC coverage through Clang, and a `compile_commands.json` for static analysis on every target. All of it must be pinned, run on three operating systems, fit a $12-a-month CI budget, and stay predictable for several AI agents working at once. Each candidate covers part of that.

**arduino-cli** is the official tool and is already in use for backups. Version **1.5.1** (June 2026, GPL-3.0) is current ([releases](https://github.com/arduino/arduino-cli/releases)). Its `sketch.yaml` profiles pin a platform and library versions per board, and while a profile builds, "the globally installed platforms and libraries are excluded from the compile" ([sketch project file](https://github.com/arduino/arduino-cli/blob/v1.5.1/docs/sketch-project-file.md)). Hardware variants become profiles with different board IDs, and `--build-property build.extra_flags=...` adds per-variant defines. `compile --only-compilation-database` writes the database without compiling, and `--dump-profile` bootstraps a pinned profile from the current setup ([compile.go](https://github.com/arduino/arduino-cli/blob/v1.5.1/internal/cli/compile/compile.go)). Every directory, including the data folder where cores install, can be redirected with `ARDUINO_*` variables or a config file passed with `--config-file` ([configuration](https://github.com/arduino/arduino-cli/blob/v1.5.1/docs/configuration.md)). That means cores can live in a git-ignored project folder instead of `~/Library/Arduino15`. Version 1.5.1 also fixed a bug where a sketch "may be wrongly considered up-to-date" ([v1.5.1](https://github.com/arduino/arduino-cli/releases/tag/v1.5.1)), which matters for CI. The limits are structural: one sketch and one board per call, and **nothing for host tests, coverage or multi-target projects**.

**PlatformIO** is the strongest single-tool option, and it deserves a fair hearing. Core **6.2.0** (September 2026, Apache-2.0) puts every board, variant and a `native` host environment in one `platformio.ini`, runs Unity, GoogleTest or doctest, writes the database with `pio run -t compiledb`, and can move its whole install with `PLATFORMIO_CORE_DIR` ([6.2.0](https://github.com/platformio/platformio-core/releases/tag/v6.2.0), [env vars](https://docs.platformio.org/en/latest/envvars.html), [compiledb](https://github.com/platformio/platformio-docs/blob/develop/integration/compile_commands.rst)). Marlin, the best-known multi-board Arduino-class firmware, uses exactly this layout, with one ini file per platform and a native Unity test environment ([Marlin ini/](https://github.com/MarlinFirmware/Marlin/tree/bugfix-2.1.x/ini)). Three things count against it here. First, the native platform uses the host compiler, "preferable based on GCC" ([native](https://github.com/platformio/platformio-docs/blob/develop/platforms/native.rst)), and no PlatformIO doc covers Clang MC/DC, so the coverage gate would be custom scripting either way. Second, **one maintainer has 5,761 commits to platformio-core, against 371 for the next** ([contributors](https://github.com/platformio/platformio-core/graphs/contributors)). Third, the official ESP32 platform shipped only Arduino-ESP32 2.0.17 from 2024 until **v8.0.0 added 3.3.12 on 19 October 2026** ([v8.0.0](https://github.com/platformio/platform-espressif32/releases/tag/v8.0.0)). The community fork pioarduino filled the gap, with documentation that is an AI-generated wiki and a README stating board issues "will not be fixed from the maintainer(s)" ([pioarduino](https://github.com/pioarduino/platform-espressif32)). Marlin's own ESP32 environments still pin espressif32 2.1.0 and 6.1.0 ([Marlin ini/](https://github.com/MarlinFirmware/Marlin/tree/bugfix-2.1.x/ini)), which shows how far PlatformIO projects drift behind.

**ESP-IDF** is the native, CMake-based framework for the ESP32-S3, actively released (v5.5.6 in October 2026, v6.1 in August 2026, Apache-2.0) ([releases](https://github.com/espressif/esp-idf/releases)). `IDF_TOOLS_PATH` and `IDF_PYTHON_ENV_PATH` move its tools and Python environment out of `~/.espressif` ([IDF tools](https://github.com/espressif/esp-idf/blob/v6.1/docs/en/api-guides/tools/idf-tools.rst)), and its Python dependencies are pinned per IDF version by a constraints file. Arduino-ESP32 is available as an official IDF component, with the warning that each Arduino version works only with a specific IDF version ([IDF component](https://github.com/espressif/arduino-esp32/blob/3.3.12/docs/en/esp-idf_component.rst)). On the AVR side, CMake is a dead end unless we build it ourselves. The Arduino-CMake projects were last pushed in 2022 and 2023, and one is archived ([Arduino-CMake-NG](https://github.com/arduino-cmake/Arduino-CMake-NG), [Arduino-CMake-Toolchain](https://github.com/a9183756-gh/Arduino-CMake-Toolchain)). A CMake UNO build therefore means our own avr-gcc toolchain file plus either compiling the LGPL Arduino core ourselves or dropping it for bare avr-libc. Bazel, Meson and Zig have no Arduino or ESP-IDF integration worth the switch. The one embedded Bazel rule set found has 20 stars ([rules_mbed](https://github.com/mjbots/rules_mbed)), and Zig's lack of an Xtensa target is **[unverified]**. QMK shows that big projects sometimes outgrow generic tools and own their build ([QMK builddefs](https://github.com/qmk/qmk_firmware/tree/master/builddefs)), which keeps "build our own" open for later.

| Option | UNO | ESP32-S3 | Host tests with Clang MC/DC | `compile_commands.json` | Pinning and home folder | Main risk |
|---|---|---|---|---|---|---|
| **Hybrid (recommended):** arduino-cli + ESP-IDF + CMake/Clang | arduino-cli profile, already installed | `idf.py`, full `sdkconfig` control | Native CMake + CTest, our flags | All three, natively | Profile versions, IDF tag, presets; all tool folders project-local | Three tools to learn and glue together |
| arduino-cli only | Yes | `esp32:esp32` core through a profile; IDF arrives as prebuilt libraries | **None** | `--only-compilation-database` | Profiles | No host tests; fixed IDF config on the S3 |
| PlatformIO only | `atmelavr` 5.3.0 | Official 8.0.0 (three weeks old) or pioarduino | `native` env, GCC by default; Clang MC/DC via custom scripts | `pio run -t compiledb` | `platformio==6.2.0` in a venv; core dir movable but untested | One main maintainer; ESP32 lag history |
| CMake superproject | Our own avr-gcc toolchain file | IDF as a sub-build | Native | Native | Needs avr-gcc installed per OS | Arduino-CMake is dead; we maintain the AVR build |
| Bazel, Meson, Zig | No Arduino integration | No IDF integration | Possible | Varies | Varies | Niche; duplicates IDF's CMake |

The hybrid wins because each part is the target's native, best-supported tool, and the shared code doesn't depend on any of them. The portable core is a plain folder of C++ with no hardware headers. CMake compiles it for host tests, arduino-cli compiles it into the UNO sketch, and an IDF component wraps it for the S3. How arduino-cli pulls in a library from a local folder (a profile entry or a `--library` flag) is **[unverified]** and is the first thing the spike must prove. Hardware variants map onto each tool's own mechanism. The UNO uses profiles, and later a `uno_r4wifi` profile. The camera board, which also exists in an ESP32-WROVER version ([camera board](../hardware/camera-board.md)), uses IDF targets and `sdkconfig.defaults` files. Host tests use presets. A small project-owned variant description that generates a header for all three would keep variant facts in one place, in the spirit of requirement D13.

For the ESP32-S3, plain ESP-IDF beats compiling Arduino-ESP32 with arduino-cli, even though arduino-cli would mean one tool for both boards. Arduino-ESP32 3.3.12 links IDF as prebuilt libraries and takes its C++ flags from a generated `cpp_flags` file ([arduino-esp32 releases](https://github.com/espressif/arduino-esp32/releases)). Settings fixed at that build, such as core dump to flash, the panic handler mode and the secure boot that requirement S12 needs, are therefore probably not ours to change **[unverified; the prebuilt sdkconfig wasn't read]**. ESP-IDF exposes all of them, adds `idf.py coredump-info` and OpenOCD debugging, and documents per-component C++ standards. Its costs are a large download (**about 1 GB or more with submodules, [unverified]**) that no system package manager provides, and the version choice. The Arduino component needs IDF 5.5.x for Arduino 3.3.12, or IDF 6.1 for the 4.0 release candidate ([3.3.12](https://github.com/espressif/arduino-esp32/releases/tag/3.3.12), [4.0.0-RC1](https://github.com/espressif/arduino-esp32/releases/tag/4.0.0-RC1)). Pure IDF can take 6.x freely. ELEGOO's own build used arduino-esp32 2.0.14 ([camera board](../hardware/camera-board.md)), which is irrelevant to a rewrite.

## The UNO stays on Arduino's avr-gcc 7.3 until a size test says otherwise

`arduino:avr` 1.8.8 (May 2026) still ships **avr-gcc 7.3.0-atmel3.6.1-arduino7 with avr-libc 2.0.0** and compiles C++ as **`-std=gnu++11`**. Neither of the last two core releases mentions a compiler change ([1.8.7](https://github.com/arduino/ArduinoCore-avr/releases/tag/1.8.7), [1.8.8](https://github.com/arduino/ArduinoCore-avr/releases/tag/1.8.8), and a measured check of the installed core's index entry and `platform.txt`). Measured: that compiler accepts `-std=gnu++17` (`__cplusplus == 201703L`) and cleanly compiled `if constexpr`, structured bindings, `inline constexpr` variables and `[[nodiscard]]` with `-fno-exceptions -fno-rtti`. It rejects C++20 (`gnu++2a`). Also measured: **the toolchain ships no C++ standard headers at all**, so `<type_traits>`, `<array>`, `<utility>` and `std::move` don't exist. The binary is **x86_64 and runs under Rosetta 2** on the maintainer's Apple-silicon Mac. That is a long-term risk if Apple retires Rosetta **[unverified timing]**. In the core's build recipe, `{compiler.cpp.extra_flags}` comes after the core's `-std=gnu++11`, so passing `-std=gnu++17` there should win, because GCC uses the last `-std`. That has been tested with `avr-g++` directly, but **not yet through arduino-cli with the Arduino core compiled as C++17**.

A newer avr-gcc is tempting but not free. GCC 15 added real AVR work: interrupt attributes that take a vector number (so ISRs can live in C++ namespaces), a compact vector table, and new size optimisations ([GCC 15 changes](https://gcc.gnu.org/gcc-15/changes.html)). GCC 16 changes the default C++ dialect to `gnu++20` ([GCC 16 changes](https://gcc.gnu.org/gcc-16/changes.html)). AVR-LibC 2.3.2 (June 2026) is current ([avr-libc](https://github.com/avrdudes/avr-libc/releases)). Against that, newer GCCs have a documented history of AVR size regressions: **a 20% regression from 8.3 to 9.1** ([GCC bug 91189](https://gcc.gnu.org/pipermail/gcc-bugs/2019-July/669715.html)), register-spill bloat from v9 through v12 ([GCC list](https://gcc.gnu.org/pipermail/gcc/2022-December/240285.html)), and the AVR maintainer keeping a GCC 8 fork alive ([avr-gcc-8](https://github.com/sprintersb/avr-gcc-8)). The stock firmware fills 98% of flash, and requirement T8 caps ours at 80% ([requirements](../requirements.md)). **On the UNO, code size decides the compiler, not language features.** Distribution makes it worse. No Homebrew core formula exists. The only Homebrew route is the third-party `osx-cross/avr` tap ([homebrew-avr](https://github.com/osx-cross/homebrew-avr)), which the maintainer's rules allow only as a last resort. Linux ranges from GCC 7.3 on Ubuntu 24.04 to 16.2 on Debian sid ([Launchpad](https://launchpad.net/ubuntu/+source/gcc-avr), [Debian](https://sources.debian.org/src/gcc-avr/)). Windows has MSYS2's 16.2 ([MSYS2](https://packages.msys2.org/base/mingw-w64-avr-gcc)), and a search found no winget package **[unverified]**. One version on all three systems would mean a third-party bundle, from Zak Kemble (16.1.0) or modm (15.3.0) ([Kemble](https://github.com/ZakKemble/avr-gcc-build/releases), [modm](https://github.com/modm-io/avr-gcc/releases)). The cleanest build-our-own route would be a small project-owned Arduino package index that points at one of those bundles. arduino-cli profiles accept a `platform_index_url` ([sketch project file](https://github.com/arduino/arduino-cli/blob/v1.5.1/docs/sketch-project-file.md)), so arduino-cli would download and pin the newer compiler project-locally on every OS. **Recommendation: keep 7.3.0 now, and once real firmware exists, build it with 7.3 and GCC 15 or 16 at `-Os -flto` and compare sizes.**

Clang is not an AVR production compiler for us. AVR is now a full LLVM target, while Xtensa is still experimental ([LLVM CMakeLists](https://github.com/llvm/llvm-project/blob/main/llvm/CMakeLists.txt)). But a November 2025 bug shows `clang --target=avr` failing to find avr-libc ([LLVM bug 168685](https://lists.llvm.org/pipermail/llvm-bugs/2025-November/135304.html)), and no source showed Clang shipping AVR firmware. Clang matters on the host instead, for tests, coverage and clang-tidy. The ESP32-S3 side is modern by comparison:

| Toolchain | Xtensa GCC | Default C++ | esp-clang shipped |
|---|---|---|---|
| ESP-IDF v5.5.6 | esp-14.2.0_20260121 | `gnu++2b` | esp-19.1.2 |
| ESP-IDF v6.0.3 | esp-15.2.0_20251204 | `gnu++26` | esp-20.1.1 |
| Arduino-ESP32 3.3.12 (IDF 5.5.5) | esp-14.2.0_20260121 | inherited from IDF, probably `gnu++2b` **[unverified]** | n/a |
| Arduino-ESP32 4.0.0-RC1 (IDF 6.1) | esp-15.2.0_20251204 | probably `gnu++26` **[unverified]** | n/a |

Sources: IDF's `tools.json` and `build.cmake` at each tag ([tools.json](https://github.com/espressif/esp-idf/blob/master/tools/tools.json), [build.cmake](https://github.com/espressif/esp-idf/blob/master/tools/cmake/build.cmake)) and Arduino-ESP32's package index at each tag ([releases](https://github.com/espressif/arduino-esp32/releases)). ESP-IDF disables exceptions and RTTI by default, and a component can set its own standard with `target_compile_options(${COMPONENT_LIB} PRIVATE -std=gnu++17)` ([IDF C++ support](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-guides/cplusplus.html)). In Arduino-ESP32, by contrast, `compiler.cpp.extra_flags` sits before IDF's flags in the recipe, so a `-std` set there would probably lose **[unverified]**. That is one more point for plain IDF. esp-clang ships with every IDF version, but nothing found calls it a supported production compiler.

## One C++17 profile, with ETL standing in for the missing standard library

AVR sets the floor: C++17 language features with no standard library. ESP-IDF's default is newer, so our components pin `gnu++17` explicitly. GoogleTest 1.17 needs C++17 on the host ([GoogleTest](https://github.com/google/googletest)). MISRA C++:2023, the project's quality yardstick, is written against C++17 ([MISRA](https://misra.org.uk/misra-cpp2023-released-including-hardcopy/)). One profile therefore fits everything, and CI enforces it by compiling the portable core with **avr-gcc 7.3, Xtensa GCC and host Clang**, so code that only a newer compiler accepts fails fast.

| Setting | Portable core (all targets) | UNO extras | ESP32-S3 extras | Host tests |
|---|---|---|---|---|
| Language | `-std=c++17` (or `gnu++17` where a framework needs GNU extensions) | Override the core's `gnu++11` via `compiler.cpp.extra_flags` **[untested via arduino-cli]** | `-std=gnu++17` per component | `-std=c++17` |
| Exceptions, RTTI | `-fno-exceptions -fno-rtti` | Core already sets `-fno-exceptions`, but not `-fno-rtti` | Off by default | Off for production code; on only in the test harness if GoogleTest needs it **[unverified]** |
| Statics, heap | `-fno-threadsafe-statics`; no heap after start-up | Already in the core's flags | | |
| Size | `-ffunction-sections -fdata-sections`, `-Wl,--gc-sections` | `-Os -flto` (core default) | IDF's optimisation setting | `-O0 -g` plus coverage flags |
| Warnings | `-Wall -Wextra -Wpedantic -Wconversion -Wshadow`, `-Werror` in CI, project code only | The core defaults to `-w` and uses `-fpermissive`, so strictness applies to our files only | | Same |
| Coverage | | | | `-fprofile-instr-generate -fcoverage-mapping -fcoverage-mcdc` |

Sources for the table: the measured `platform.txt` flags (`-fno-exceptions -ffunction-sections -fdata-sections -fno-threadsafe-statics -flto`, no `-fno-rtti`, `-w` by default), ArduPilot's embedded flags `-fno-exceptions -fno-rtti -fno-threadsafe-statics` ([boards.py](https://github.com/ArduPilot/ardupilot/blob/master/Tools/ardupilotwaf/boards.py)), IDF's C++ guide ([IDF](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-guides/cplusplus.html)) and Clang's MC/DC flag ([Clang coverage](https://clang.llvm.org/docs/SourceBasedCodeCoverage.html)). The warning set is a starting point drawn from common practice, not a measured result.

**ETL is the standard-library replacement**: release **20.49.0** (September 2026), MIT-licensed, and it "avoids dynamic memory allocation entirely; the heap is never used", needs no STL (`ETL_NO_STL`) and no RTTI, and works with any compiler from C++03 up ([ETL releases](https://github.com/ETLCPP/etl/releases), [README](https://github.com/ETLCPP/etl/blob/master/README.md)). RIOT-OS packages it ([RIOT](https://git.riot-os.org/RIOT-OS/RIOT/raw/commit/021720a995a9cf91190c5a3a91ad8b27aff45543/pkg/etl/doc.txt)). The alternatives are weaker. ArxContainer has been dormant since June 2024 ([ArxContainer](https://github.com/hideakitai/ArxContainer)). ArduinoSTL is a uClibc++ port with heap-allocating containers, last released in 2022, and GitHub detects its licence as GPL-3.0 ([ArduinoSTL](https://github.com/mike-matera/ArduinoSTL)). That would be a copyleft problem for Apache-2.0 firmware if the detection is right. The project should pin ETL by exact version and **define `ETL_NO_STL` on every target, not just AVR**, so the host tests exercise the same container code the UNO runs. ETL publishes no AVR CI badge, so its avr-gcc 7.3 behaviour is ours to prove in the spike. A few rules follow from the AVR floor: the portable core includes no standard C++ headers, only `etl/` and C headers from avr-libc; it never assumes 64-bit `double`, which is 32-bit on avr-gcc 7.3 **[unverified]**; and, as in the coverage gate, decisions stay at six conditions or fewer so every Clang version reports MC/DC ([Clang 18 docs](https://prereleases.llvm.org/18.1.0/rc3/tools/clang/docs/SourceBasedCodeCoverage.html)).

Host tests then follow the plan the quality gates already set. CMake (4.4.5 is current; presets support toolchain files and workflow presets ([CMake releases](https://github.com/Kitware/CMake/releases), [cmake-presets](https://cmake.org/cmake/help/latest/manual/cmake-presets.7.html))) builds GoogleTest suites, and CTest runs them. A `host-coverage` preset turns on Clang's MC/DC flags. **Apple Clang 21 on the maintainer's Mac already produces MC/DC with nothing installed**, but `llvm-cov` has no fail-under option and its LCOV export drops MC/DC, so a short Python script reads the JSON summary and fails the build below 100% (measured on 8 November 2026). A `host-gcc` or `host-msvc` preset can exist purely as a compile check. Whether MC/DC works with Clang on Windows is still **[unverified]**.

## Python, uv and just carry the workflow across three systems

The glue should be a task runner whose recipes each run one cross-platform program, with any real logic in Python. **just** fits best. It runs on Linux, macOS and Windows, is CC0-licensed, and installs from Homebrew (`brew install just`), winget (`Casey.Just`), Scoop, apt on Debian 13 and Ubuntu 24.04, dnf and pacman ([just packages](https://just.systems/man/en/packages.html), [just](https://github.com/casey/just)). It is also on PyPI as `rust-just` ([packages](https://just.systems/man/en/packages.html)), so the project could pin it in its own uv environment and install nothing system-wide. The catch is that recipes run in `sh` unless a `windows-shell` setting picks PowerShell ([just manual](https://just.systems/man/en/)), and the exact setting syntax is **[unverified]**. Keeping every recipe to one command (`uv run tools/coverage.py`, `arduino-cli compile --profile uno`, `idf.py build`, `cmake --workflow --preset host-coverage`) makes the shell irrelevant, and `just --list` documents the commands for contributors and AI agents alike. Make is the weakest choice on Windows, Taskfile is a credible YAML alternative, and a pure uv-plus-nox setup avoids a second binary at the cost of less discoverable commands (all **[unverified]**). uv is already the Python tool the quality-gate plan chose, with a committed `uv.lock` and `uv sync --locked` in CI ([uv](https://docs.astral.sh/uv/concepts/projects/sync/)).

**pre-commit 4.7.0** goes in the same uv environment. It is tested on Windows for Python-, Go- and Rust-based hooks, but not for Docker or Swift hooks, and Node and Ruby hooks "may work" there ([pre-commit](https://pre-commit.com/)). So hooks should be Python wheels or prebuilt binaries: clang-format from its pip mirror, the standard `pre-commit-hooks` set, REUSE, and a secret scanner for the Wi-Fi password **[hook choices unverified]**. prek, a Rust rewrite that reads the same config with no Python, is faster but still missing "some subcommands and languages" ([prek](https://pypi.org/project/prek/0.2.29/)), so it is a later swap, not a starting point. One conflict needs solving first. The repo already sets `core.hooksPath` to `.githooks` for its pre-push guard ([tools.md](../tools.md)), and pre-commit is understood to refuse installing when `core.hooksPath` is set **[unverified]**. The clean fix is a committed `.githooks/pre-commit` that calls `uv run pre-commit run`, which keeps one hook mechanism.

**Containers should stay optional and build-only.** Builds in a container work everywhere, but flashing from one doesn't. Espressif states that on macOS "USB passthrough is not yet supported". Windows needs usbipd-win attaching the device to WSL first ([Espressif docs](https://docs.espressif.com/projects/vscode-esp-idf-extension/en/latest/additionalfeatures/docker-container.html)). esptool can flash over the network through an RFC2217 bridge ([Docker blog](https://www.docker.com/ja-jp/blog/reproducible-esp32-firmware-development-with-docker-and-docker-sandboxes/)), but JTAG is not a serial protocol and can't use that bridge. A Golioth post claims Docker Desktop 4.35 reaches USB devices on macOS ([Golioth](https://blog.golioth.io/usb-docker-windows-macos/)), which contradicts Espressif and is untested. The UNO also needs a hand on its Upload-Cam switch for every flash ([hardware](../hardware/README.md)). Build, flash, monitor and debug from host tools, then. Since arduino-cli and ESP-IDF can both put their tools in a project folder, a container isn't needed to keep machines clean.

For editors, the portable choice is **clangd**, reading each target's `compile_commands.json`, with a committed `.clangd` that strips GCC-only flags such as `-mmcu` and `-mlongcalls`. clangd speaks LSP, so it works in any editor and for agents that use LSP. Only `.vscode/extensions.json` gets committed. Microsoft's C/C++ extension, which PlatformIO uses, writes machine-specific absolute paths. All of this is common practice but **[unverified]** in this research. Static analysis uses the same databases. arduino-cli and PlatformIO generation are documented above, and ESP-IDF is said to write one by default **[unverified]**. clang-tidy can't target Xtensa in mainline LLVM ([LLVM CMakeLists](https://github.com/llvm/llvm-project/blob/main/llvm/CMakeLists.txt)), so it runs on the portable core with the host target. Board-specific files are checked with filtered flags, or with the esp-clang that IDF ships.

Two workflow details matter for several agents at once. First, project-local tool folders are good for cleanliness, but each git worktree would download its own ESP-IDF. The task runner should therefore point `ARDUINO_DIRECTORIES_DATA`, `IDF_TOOLS_PATH` and `IDF_PYTHON_ENV_PATH` at one git-ignored folder in the main checkout, found through git's common directory, so all worktrees share it **[untested design]**. Whether arduino-cli resolves relative paths in its config file against the file or the working directory is also untested ([configuration](https://github.com/arduino/arduino-cli/blob/v1.5.1/docs/configuration.md)). Second, the CI budget shapes what runs per pull request. GitHub Free gives **$12 of compute a month at $0.006 a minute on Linux, $0.010 on Windows and $0.062 on macOS** ([GitHub billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)). So each pull request runs a Linux job: UNO build, host tests, coverage and clang-tidy. The ESP-IDF build runs only when ESP32 or portable-core paths change, and Windows and macOS run less often until the repo is public. CI caches the tool folders keyed on `sketch.yaml`, the IDF tag and the presets file, and ccache 4.14.3 serves the host build ([ccache](https://github.com/ccache/ccache/releases)). The official `arduino/setup-arduino-cli` and Espressif CI actions, and their current versions, are **[unverified]**.

## The ESP32-S3 debugs over its cable; the UNO's breakpoints need a hardware change

The ESP32-S3 is the easy board. Its USB-Serial/JTAG peripheral on GPIO19 and GPIO20 gives OpenOCD and GDB breakpoint debugging "without any additional chip" ([ESP-IDF JTAG](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-guides/jtag-debugging/configure-builtin-jtag.html)), and our camera board wires its USB-C port straight to those pins ([camera board](../hardware/camera-board.md)). Linux needs OpenOCD's udev rule and Windows a driver installed by Espressif's tool. macOS needs nothing, according to the same docs. Post-mortem analysis is configuration only. The stock flash layout already has a core dump partition (measured: [camera backup](../notebook/2026-11-06-backing-up-the-camera-board.md)), `idf.py coredump-info` and `coredump-debug` decode it, and the panic handler can drop into a GDB stub that reads but can't set breakpoints ([core dump](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-guides/core_dump.html), [fatal errors](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-guides/fatal-errors.html)). Two cautions follow. Our firmware must keep USB in its hardware CDC-and-JTAG mode rather than switching to TinyUSB, and must never burn the eFuse that disables USB-JTAG **[unverified]**. Check that secure-boot settings for S12 don't disable JTAG by default **[unverified]**. The bigger problem is power. The USB-C port's 5 V connects straight to the robot's 5 V rail through the link cable, with no diode ([camera board](../hardware/camera-board.md)), so **debugging the S3 while it talks to the UNO back-feeds the rail**. A USB data-only adapter that blocks 5 V would avoid that without changing the robot, but whether one works with this port is **[unverified]**.

The UNO is the hard board, and requirement D12 ("stop at a breakpoint on each board", stage 2) makes it urgent ([requirements](../requirements.md)). Real breakpoints on an ATmega328P need debugWIRE. The cheap modern route is an **MPLAB SNAP at about US$11.46–12.76** from authorized distributors in mid-2026 (AU$18.74 at element14; some listings reach US$64–74) ([mymectronic](https://www.mymectronic.com/part-detail/Microchip-Technology/PG164100), [element14](https://au.element14.com/microchip/pg164100/in-circuit-debugger-1-2v-to-5/dp/2915518), [Digi-Key](https://www.digikey.gr/en/product-highlight/m/microchip-technology/pg164100-snap-debugger)). It is driven by **PyAvrOCD**, a cross-platform GDB server for EDBG-class probes that reached 1.0.0 in February 2026 and plugs into avr-gdb, Arduino IDE 2 and PlatformIO ([PyAvrOCD](https://github.com/felias-fogg/PyAvrOCD)). dw-link turns a classic AVR UNO into a probe instead, but its manual recommends the SNAP "for a more durable solution" ([dw-link](https://felias-fogg.github.io/dw-link/latest/)). The maintainer's UNO R4 WiFi has an Arm chip and almost certainly can't host it (inference). Bloom is Linux-only ([Bloom](https://www.github.com/bloombloombloom/Bloom)), and avarice needs legacy probes ([avarice](https://manpages.debian.org/unstable/avarice/avarice.1.en.html)).

**Hardware change flag:** debugWIRE needs the UNO's auto-reset capacitor disconnected from RESET. On a genuine UNO R3 that means cutting the "RESET EN" trace; on clones it can mean removing the capacitor **[unverified]**. Our board is an R3-compatible clone with a CH340 USB chip and Optiboot 4.4 ([UNO backup](../notebook/2026-11-04-backing-up-the-uno.md)), and nobody has checked whether it even has a RESET EN pad. Setting the debugWIRE fuse also needs ISP access, and debugging overwrites the bootloader, which then has to be restored over ISP **[unverified]**. That also touches D6, returning to stock. Decision 0001 defers hardware changes ([0001](../decisions/0001-stock-hardware-first.md)), so on-robot debugWIRE is not available without the maintainer's explicit exception.

Without touching the robot, three paths remain. **simavr** runs firmware as a GDB server (`simavr -g -m atmega328p`), and avr-gdb connects to it ([simavr man page](https://manpages.ubuntu.com/manpages/noble/man1/simavr.1.html)). It is packaged on Ubuntu, but on macOS it comes from the third-party tap ([homebrew-avr](https://github.com/osx-cross/homebrew-avr)), and Windows support is weak **[unverified]**. **Wokwi** simulates more parts and has CI, but it is closed SaaS, its VS Code extension is paid, and its CI quotas conflict between pages ([pricing](https://wokwi.com/pricing), [CI docs](https://docs.wokwi.com/wokwi-ci/getting-started)). **In-firmware diagnostics** cost bytes rather than hardware **[all unverified against the datasheet and avr-libc docs]**: capture the reset cause from MCUSR at start-up, keep breadcrumbs in `.noinit` RAM across watchdog resets, use a compact assert that sends a file ID and line over the link, and paint the stack to report its high-water mark. These also serve requirement D11's "unexpected reset" fault. A fourth path keeps the robot unchanged by putting debugWIRE on a **separate, inexpensive UNO-compatible bench board**, modified freely and used for code that doesn't need the shield. Whether that counts as a hardware change under 0001 is the maintainer's call.

| Board | Method | Gives | Cash cost | Hardware change? |
|---|---|---|---|---|
| ESP32-S3 | USB-JTAG + OpenOCD + GDB (from ESP-IDF) | Full breakpoints, stepping | None | No. Mind the 5 V back-feed with the link connected |
| ESP32-S3 | Core dump, panic GDB stub, backtrace decoding | Post-mortem state | None | No |
| UNO | Host tests on the portable core | Most logic bugs, with MC/DC | None | No |
| UNO | In-firmware reset cause, breadcrumbs, asserts | Crash location, reset cause | Flash and RAM bytes | No |
| UNO | simavr + avr-gdb | Breakpoints in simulation, no peripherals beyond basics | None | No |
| UNO | Wokwi | Simulation with parts, CI | Free tier; paid editor extension | No |
| UNO | MPLAB SNAP + PyAvrOCD on a spare bench UNO | Real on-chip breakpoints, off the robot | About US$12–20 plus a clone board | Not on the robot |

## Gaps stated honestly

The biggest gap is that **the recommended UNO path has not been built end to end**. Nobody has compiled the Arduino core as C++17 through arduino-cli, loaded the portable core as a local library into a profile, used project-local relative directories on all three OSes, or fed arduino-cli's database to clang-tidy. These are the spike's first four tasks. Code size across avr-gcc 7.3, 15 and 16 is unknown for our firmware, and no 2025–2026 benchmark exists. ETL has no published avr-gcc 7.3 testing. On the ESP32 side, the prebuilt Arduino sdkconfig wasn't read, IDF's `compile_commands.json` behaviour and lock-file handling in 6.x weren't confirmed, IDF's long-term support windows weren't researched, and its Windows host-test target probably doesn't exist ([host apps](https://github.com/espressif/esp-idf/blob/v6.1/docs/en/api-guides/host-apps.rst)). Windows is the least proven platform overall: Clang MC/DC, the Clang install footprint, just's shell setting and several winget IDs are all **[unverified]**. Editor setup and every in-firmware AVR diagnostic technique rest on general knowledge, with no fetched source. The debugWIRE requirements for this particular clone board are unknown. PlatformIO Labs' funding and staffing, and Rosetta 2's retirement date, have no primary source. Finally, no open project was found that combines an ATmega328P and an ESP32-S3 in one repo with one build, so this layout has no direct precedent to copy.

## Decisions for the maintainer

1. **Build architecture:** the hybrid (arduino-cli for the UNO, ESP-IDF for the S3, CMake and Clang for host tests) or PlatformIO for everything, accepting its maintainer and ESP32-lag risks for one config file.
2. **Arduino core on the UNO:** keep the Arduino core behind the project's own hardware layer (recommended to start), or write bare avr-libc code and own the AVR build entirely, saving flash at the cost of more code we maintain. Decide after the size spike.
3. **AVR compiler:** stay on Arduino's avr-gcc 7.3 now (recommended), and schedule a size comparison against GCC 15 or 16. If a newer one wins, choose how to ship it: a project-owned Arduino package index, a third-party bundle, or distro packages.
4. **Language level:** C++17 on every target (recommended), with `gnu++17` only where a framework needs it, and CI compiling the portable core with all three compilers.
5. **ETL:** adopt ETL pinned at 20.49.0. Decide whether `ETL_NO_STL` applies to every target (recommended) or only the UNO, and whether to vendor it or fetch it by exact version.
6. **ESP32-S3 framework and version:** plain ESP-IDF, ESP-IDF with the Arduino component, or arduino-cli's ESP32 core; and which IDF line to pin (5.5.x for Arduino 3.3, or 6.x).
7. **Task runner:** just installed through the system package manager, just pinned as `rust-just` in the project environment, or uv and nox with no just at all.
8. **Hooks:** pre-commit in `.venv`, called from `.githooks/pre-commit` so the pre-push guard stays, or prek; and which secret scanner to add.
9. **Tool locations:** move arduino-cli's data folder and ESP-IDF's tools into one shared, git-ignored project folder, then remove the global `arduino:avr` core once backups use the project copy.
10. **Containers:** none for daily work now (recommended), with a CI-only image considered later if CI setup time hurts the budget.
11. **Editor default:** document clangd with per-target databases, and commit only `.vscode/extensions.json` plus a `.clangd` file.
12. **UNO debugging and D12:** pick one. Meet D12 on the UNO with simavr plus in-firmware diagnostics in stage 2 and amend the requirement's wording. Buy a SNAP and a spare bench UNO, which leaves the robot unchanged. Or grant an exception to 0001 for the reversible auto-reset change on the robot.
13. **ESP32 debugging with the link connected:** unplug the link while debugging, or test a USB adapter that blocks 5 V.
14. **CI shape:** which builds run on every pull request under the $12 budget. The suggestion is UNO build, host tests, coverage and clang-tidy on Linux every time, the ESP-IDF build only when its paths change, and Windows and macOS less often.

## Conclusion

The toolchain question turned out to be mostly an architecture question. Once the board-independent logic lives in a plain C++17 folder with no hardware headers and ETL instead of the standard library, the build tools become replaceable adapters, and the hybrid's extra moving parts cost little. The same boundary that makes 100% MC/DC honest also lets arduino-cli, ESP-IDF and CMake coexist without any of them owning the code. The constraint that really shapes the UNO is the flash budget, not C++ features: the decision between the comfortable, Rosetta-bound GCC 7.3 and a modern compiler should rest on a measured byte count.

The sharpest finding is a clash between two of the project's own rules. D12 asks for breakpoints on both boards in stage 2, while decision 0001 defers the one hardware change that makes UNO breakpoints possible. The ESP32-S3 has its own quieter version of the same problem: its debugger cable back-feeds the robot's power rail. Settling both before the first firmware commit is cheaper than discovering them at the first crash.
